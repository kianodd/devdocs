Creating Heap-Allocated Types

The following function is used to create heap types :

Create and return a heap type from a :c`!PySlot` array. See capi-slots for general information on slots, and pyslot_type_slot_ids for slots specific to type creation.

This function calls :c`PyType_Ready` on the new type.

Note that this function does not fully match the behavior of calling :py`type() [ or using the `class] statement. With user-provided base types or metaclasses, prefer calling :py`type` (or the metaclass) over PyType_From* functions. Specifically:

  • :py`~object.__new__` is not called on the new class (and it must be set to type.__new__).
  • :py`~object.__init__` is not called on the new class.
  • :py`~object.__init_subclass__` is not called on any bases.
  • :py`~object.__set_name__` is not called on new descriptors.

Slots are typically defined as a global static constant arrays. However, sometimes slot values are not statically known at compile time. For example, slots like :c`Py_tp_bases`, :c`Py_tp_metaclass` and :c`Py_tp_module` require live Python objects. In this case, it is recommended to put such slots on the stack, and use :c`Py_slot_subslots` to refer to an array of static slots. For example:

Heap types created without the :c`Py_TPFLAGS_IMMUTABLETYPE` flag may be modified, for example by setting attributes on them, as with classes defined in Python code. Sometimes, such modifications are necessary to fully initialize a type, but you may wish to prevent users from changing the type after the initialization is done:

Make a type immutable: set the :c`Py_TPFLAGS_IMMUTABLETYPE` flag.

All base classes of type must be immutable.

On success, return 0. On error, set an exception and return -1.

The type must not be used before it's made immutable. For example, type instances must not be created before the type is made immutable.

Type slot IDs

Most type slot IDs are named like the field names of the structures :c`PyTypeObject`, :c`PyNumberMethods`, :c`PySequenceMethods`, :c`PyMappingMethods` and :c`PyAsyncMethods` with an added Py_ prefix. For example, use:

  • :c`Py_tp_dealloc` to set :c`PyTypeObject.tp_dealloc`
  • :c`Py_nb_add` to set :c`PyNumberMethods.nb_add`
  • :c`Py_sq_length` to set :c`PySequenceMethods.sq_length`

The following slots need additional considerations when specified as slots:

  • :c`Py_tp_name`
  • :c`Py_tp_basicsize` and :c`Py_tp_extra_basicsize`
  • :c`Py_tp_itemsize`
  • :c`Py_tp_flags`

Additional slots do not directly correspond to a :c`!PyTypeObject` struct field:

  • :c`Py_tp_token`
  • :c`Py_tp_metaclass`
  • :c`Py_tp_module`

The following "offset" fields cannot be set using :c`PyType_Slot`:

  • :c`~PyTypeObject.tp_weaklistoffset` (use :c`Py_TPFLAGS_MANAGED_WEAKREF` instead if possible)
  • :c`~PyTypeObject.tp_dictoffset` (use :c`Py_TPFLAGS_MANAGED_DICT` instead if possible)
  • :c`~PyTypeObject.tp_vectorcall_offset` (use "__vectorcalloffset__" in PyMemberDef )

If it is not possible to switch to a MANAGED flag (for example, for vectorcall or to support Python older than 3.12), specify the offset in :c`Py_tp_members`. See PyMemberDef documentation for details.

The following internal fields cannot be set at all when creating a heap type:

  • :c`~PyTypeObject.tp_dict`, :c`~PyTypeObject.tp_mro`, :c`~PyTypeObject.tp_cache`, :c`~PyTypeObject.tp_subclasses`, and :c`~PyTypeObject.tp_weaklist`.

The :c`Py_tp_base` slot is equivalent to :c`Py_tp_bases`; both may be set either to a type or a tuple of types. If both are specified, the value of :c`Py_tp_bases` is used.

Slot values may not be NULL, except for the following:

  • :c`Py_tp_doc`
  • :c`Py_tp_token` (for clarity, prefer :c`Py_TP_USE_SPEC` rather than NULL)

:c`Slot ID [ for the size of one element of a variable-size type, in bytes. Used to set :c`PyTypeObject.tp_itemsize]. See :c`!tp_itemsize` documentation for caveats.

The value must be positive.

If this slot is missing, :c`~PyTypeObject.tp_itemsize` is inherited. Extending arbitrary variable-sized classes is dangerous, since some types use a fixed offset for variable-sized memory, which can then overlap fixed-sized memory used by a subclass. To help prevent mistakes, inheriting itemsize is only possible in the following situations:

  • The base is not variable-sized (its :c`~PyTypeObject.tp_itemsize` is zero).
  • The requested :c`PyType_Spec.basicsize` is positive, suggesting that the memory layout of the base class is known.
  • The requested :c`PyType_Spec.basicsize` is zero, suggesting that the subclass does not access the instance's memory directly.
