Is sharding appropriate for a new deployment?

Sometimes. However, if your data set fits on a single server, you should begin with an unsharded deployment as sharding while your data set is small provides little advantage .

Why are my documents not distributed across the shards?

The balancer starts distributing data across the shards once the distribution of chunks has reached certain thresholds. See sharding-migration-thresholds.

In addition, MongoDB cannot move a chunk if the number of documents in the chunk exceeds a certain number. See migration-chunk-size-limit and jumbo-chunk.

How does mongos detect changes in the sharded cluster configuration?

[~bin.mongos] instances maintain a cache of the config database that holds the metadata for the sharded cluster.

[~bin.mongos] updates its cache lazily by issuing a request to a shard and discovering that its metadata is out of date. To force the [~bin.mongos] to reload its cache, you can run the [flushRouterConfig] command against each [~bin.mongos] directly.

How does mongos use connections?

Each [~bin.mongos] instance maintains a pool of connections to the members of the sharded cluster. Client requests use these connections one at a time; i.e. requests are not multiplexed or pipelined.

When client requests complete, the [~bin.mongos] returns the connection to the pool. These pools do not shrink when the number of clients decreases. This can lead to an unused [~bin.mongos] with a large number of open connections. If the [~bin.mongos] is no longer in use, it is safe to restart the process to close existing connections.
