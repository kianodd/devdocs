A plain Jsonb column, Prisma ORM 8's type for a PostgreSQL jsonb column, reads as any JSON value, so your code has to check what is in it. The arktype-json extension describes a JSON column with an arktype schema instead. The column's TypeScript type then comes from the schema, and Prisma ORM checks each value against the schema when it reads it.

The column is still a jsonb column, so it needs nothing installed on the server.

This page assumes a Prisma ORM 8 project on PostgreSQL, such as one from Create a new app with PostgreSQL, where src/prisma/db.ts creates the client your code queries with.

Your contract must be TypeScript

The schema is a JavaScript value, so the column is declared in a TypeScript contract, src/prisma/contract.ts; a contract.prisma contract cannot hold it. A project has one contract, so if yours is contract.prisma, rewrite it in TypeScript first: TypeScript schema builder shows the TypeScript form of each PSL construct. Then set contract in prisma.config.ts to ./src/prisma/contract.ts.

Then update the generated files, write the migration, and apply it to your development database:

Two changes leave the database as it is, because the column stays jsonb: switching an existing Jsonb column to arktypeJson(...), and changing the arktype type later. After either one, run npx prisma contract emit so the column's TypeScript type follows. migration plan then stops with MIGRATION.PLANNING_FAILED and prints a command:

  1. Run the printed npx prisma migration new --from <hash>. It writes a migration with no operations, which records the new contract.
  2. Run npx prisma db migrate --advance-ref db.

Rows already in the column are not checked until they are read.

Read and write the column

contract emit writes the schema's TypeScript type into contract.d.ts, so meta reads as { tags: string[]; readingMinutes?: number }, and TypeScript checks what you write:

Prisma ORM checks a value against the schema when it reads it, not when it writes it. A row whose stored value breaks the schema, written by SQL or by another app, fails to read with an error whose code is RUNTIME.JSON_SCHEMA_VALIDATION_FAILED, and the message names the problem, such as tags must be an array (was number). In a query that returns many rows, one such row fails the whole query.

Because writes are not checked, a value typed any or unknown, such as a parsed request body, reaches the database unchecked. What happens next depends on the method:

  • create() saves the row, then throws RUNTIME.JSON_SCHEMA_VALIDATION_FAILED when it reads the row back. The row stays in the database.
  • update() throws the same error and does not save the change.
  • createAndCount() and updateAndCount() do not read rows back, so they save the value and throw nothing.

Check such a value with the arktype type before you write it:

To repair a row that fails to read, overwrite its value: update() does not read the old value, so db.orm.public.Article.where({ id }).update({ meta: { tags: [] } }) works on it. Find such rows with SQL, such as SELECT id FROM article WHERE meta IS NOT NULL AND jsonb_typeof(meta->'tags') IS DISTINCT FROM 'array', which also finds values with no tags key; the table is article because the contract sets table: 'article'.
