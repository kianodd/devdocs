Fastify, Express and Hono route requests to your handlers, and you choose or write what goes around them. Nest organizes the whole backend, with modules, dependency injection, guards, pipes and first-party packages, and it runs on top of Express, Fastify or Node's own node:http. So Nest doesn't replace Fastify or Express: they can be what it runs on. This page helps you choose.

When to use which

What you're building Better fit Why
A backend that will grow: more modules, more developers, a database, background jobs Nest Modules, dependency injection, guards and pipes give it one structure, and services are easy to test
An enterprise-grade system, with many teams and a long-lived codebase Nest Every team works in the same structure, and the core team offers enterprise support
A small API with authentication, validation and a database Nest or Fastify nest new --minimal starts from one file, and first-party packages add the rest. Fastify does the same with plugins and less code around each route
Microservices over Kafka, RabbitMQ, NATS or gRPC Nest The transports are first-party and share one programming model
A service that will stay a few routes, such as a proxy or a webhook receiver Fastify or Hono There's nothing to organize
An API on Cloudflare Workers or another edge runtime Hono It's built on Web Standards and runs there natively. See Cloudflare Workers
A Next.js frontend sharing route types with its API, with no code generation Hono Its RPC client infers types from the routes. With Nest, a shared package holds the schemas and types instead
An Express application that already works Express, or Nest one route at a time Migrating from Express runs both side by side
The highest request rate on routes that do very little Fastify It's a few percent ahead of Nest. See Performance

How small a Nest application can be

nest new my-api --minimal generates an application whose code is one file, src/main.ts:

It stays the same application as it grows. nest g resource users adds a module, and when src/main.ts gets long, you move the root module to its own file. See One-file projects.

Fastify, Express and Hono start with fewer lines, which stays an advantage while the application stays small. As it grows, where authentication lives, how its parts share services, and how tests replace dependencies become yours to design. Nest decides those up front.

Performance

Requests per second on GET /, with each server answering Hello world!, using wrk -t4 -c100 for 8 seconds after a 3-second warm-up, on Node.js 24.20. Each number is the median of 3 rounds:

Server GET /
Fastify 57.1k
Nest on Node 55.6k
Hono on Node 53.1k
Nest on Fastify 52.6k
Express 37.0k
Nest on Express 37.0k

So with the NodeAdapter, Nest handled about 3% fewer requests per second than plain Fastify, about 5% more than Hono on Node, and about 50% more than plain Express.

A separate round on an M1 Pro, with a route parameter and a JSON body:

Server GET /users/:id POST /echo (JSON)
Express 35.6k 30.1k
Fastify 54.0k 43.5k
Nest on Express 34.5k 28.2k
Nest on Fastify 48.4k 40.2k
Nest on Node 51.0k 42.4k

Here Nest on Node came within 3-6% of plain Fastify and stayed 41-43% ahead of plain Express.

To run these yourself, follow the steps in nestjs/nest#18063, which also have the servers for Hono, Koa, Elysia and AdonisJS. Other machines give different gaps, and Hono's number covers only Node, not the other runtimes it runs on.

These routes do almost no work. A route that queries a database or calls other services spends most of its time waiting for them, so for most applications these differences won't decide the choice.

Moving to Nest later

The choice doesn't have to be final:

  • From Fastify, Nest runs on the same server through the FastifyAdapter, and your plugins keep working. See Migrating from Fastify.
  • From Express, routes move one at a time with both serving requests, or all at once. See Migrating from Express.
