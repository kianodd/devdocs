A production PostgreSQL database usually has more than tables and foreign keys: policies that decide which rows a user may see, indexes over expressions, constraints that reject bad values, tables that another system owns, and extensions such as citext. Prisma ORM 8 supports all of these in contract.prisma, the file that replaced schema.prisma. This page shows each one in the situation it solves. After every change to the contract, you run the same three commands: npx prisma contract emit, which turns contract.prisma into the contract.json and contract.d.ts files your app and the CLI read, then npx prisma migration plan --name <name>, which writes a migration, then npx prisma db migrate --advance-ref db, which applies it to your development database. Generating a migration walks through them. The syntax and every option are on Author in PSL, with the TypeScript form on Author in TypeScript. Limitations lists what the contract cannot say yet, and what to do instead.

Every SQL expression on this page is a sql`...` literal, not a quoted string, and it uses column names, not field names. The two differ only when a field has @map. Nothing checks the SQL until the migration runs it.

Rows that belong to a user

Your document table holds every user's documents, and each user may read and change only their own. PostgreSQL enforces that with row-level security: policies on the table, applied to the database role your app connects as. Turn it on for the model with @@rls, name the role, and write a policy block for each operation you want to allow. expression: replaces the field list, and where: is the condition without the WHERE keyword. unique: makes a unique index, and type: picks the index method, such as "gin" for a list column. The index in the database is named after name: with a short suffix, such as user_email_lower_000a85d8. Changing name: later renames the index; it does not rebuild it. map: is for an index that already exists in the database, and sets its exact name; for a new index, use name:. A table Prisma ORM should not touch

An audit_log table is written by a database trigger and owned by the operations team, and a legacy_customer table is shared with another application. You want to read both from your app without migration plan ever altering them. @@control says how far Prisma ORM manages a table:

Value db verify Migrations
managed (the default) The table must exist and match the model exactly. Create, alter, and drop it.
tolerated Declared columns must match; extra columns are accepted. Create it if missing; never alter or drop it.
external Declared columns must match; extra columns and constraints are ignored. Never touch it.
observed Anything goes; a mismatch is a warning, not a failure. Never touch it.

tolerated fails db verify on a changed or missing declared column but accepts columns it does not know; external also ignores constraints it does not know, and never creates the table. Pick external when the table always exists before Prisma ORM arrives and its declared columns are stable, and observed when even those columns may change under you. Control policy is the reference entry; it is unrelated to the row-level security policies above.

A Prisma extension package such as pgvector declares its PostgreSQL extension in its own contract, so for those you declare nothing.

Adopting these from an existing database

npx prisma contract infer --db "$DATABASE_URL" reads a live database and writes a starter contract. It writes each index, check constraint, and policy it finds with map: (@@map on a policy) set to the name the database has, and with the SQL as PostgreSQL stores it, so db verify matches them and migration plan leaves them alone. From then on the rule is: map: for something that already exists in the database under that exact name, name: for something you are adding. Each contract emit on such a contract prints a PN_EXACT_NAME_BODY_COMPARISON warning for every policy, check, and index that has SQL in it and uses map: or @@map. The warnings are expected, and nothing needs to change.

Limitations

These are the gaps at 8.0.0-rc.23, each with what to do instead. Anything the contract cannot say yet goes in a raw SQL step in a migration, which runs the statements you give it. npx prisma migration new --name <name> --from <hash> creates a migration with no operations; migration new explains --from, which the command needs when the contract has not changed. The step goes in its operations list, with rawSql imported from @prisma/orm-postgres/migration. Recompile the file afterwards, as Editing a migration shows. operationClass is additive, widening, destructive, or data, and the GRANT below loosens a rule, so it is widening. Raw SQL in the migration API reference has the full shape:

  • Roles and GRANT are not part of the contract. Prisma ORM creates policies but never creates a role or grants privileges to one. Create the role and run the GRANT statements in a raw SQL step, or by hand.
  • FORCE ROW LEVEL SECURITY is not part of the contract. Row-level security as Prisma ORM declares it does not apply to the table's owner. To make it apply to the owner too, run ALTER TABLE ... FORCE ROW LEVEL SECURITY in a raw SQL step. Even then a superuser, or a role with BYPASSRLS, is never filtered, so the role your app logs in as must be neither.
  • Triggers and functions are not part of the contract. Create them in a raw SQL step.
  • A sort order inside @@index is refused. @@index([createdAt(sort: Desc)]) fails with "Expected a field name" (prisma/orm#30270). Create such an index in a raw SQL step.
  • A variant that shares its base model's table loses its own constraints. A variant is a model that extends another with @@base, the way Bug extends Task on the PSL page; one with no @@map of its own stores its rows in the base model's table. A foreign key, @@unique, or @@index declared on it is dropped from the contract without a warning (prisma/orm#30445), and @@check on it is refused. Declare them on the base model, or give the variant its own @@map so it gets its own table. Base models and variants covers the two layouts.
  • SQL you wrote yourself with map: can report drift. db verify compares the SQL in the contract with the text PostgreSQL stores, and PostgreSQL rewrites what it is given. Inferred SQL matches, because contract infer writes back PostgreSQL's text; SQL you typed with map: may not (prisma/orm#30294). Use name: for anything you add.
  • contract infer reads only the public schema (prisma/orm#30573). Policies, indexes, and tables in other schemas are not read back; write them by hand. It also skips a policy whose role name is not a valid PSL name, and any index, check, or policy whose SQL it cannot read back unchanged, and leaves a comment in the file where it did.
  • A generated check cannot be waived. Prisma ORM always adds a check on an enum column so it accepts only the enum's values, and on a list column so it rejects NULL elements. On a table whose control policy is managed, it also adds one on each value object column, which accepts only the value object's shape, and one on a discriminator column, which accepts only its variants' values. A migration that adds such a check fails on a row the check refuses, and the error gives the query that finds those rows. Declare a list String?[] when its elements may be NULL. The @noCheck attribute that used to waive these was removed in 8.0.0-rc.19.
