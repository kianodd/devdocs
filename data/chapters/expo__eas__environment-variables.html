This guide explains how to use Environment Variables in Expo Services: Build, Updates, Workflows, and Hosting. For general information on how environment variables work with the Expo framework, refer to Environment variables in Expo.

During local development, environment variables are loaded from your local .env or .env.local files. These files are generally excluded from the project's version control (that is, if they are listed in the .gitignore file or not committed) so they are not available for jobs that run on a remote server, for example, Expo Build and Expo Workflows. Additionally, most projects have multiple app variants and require multiple sets of environment variables (for instance Development and Production).

Why use Expo Services environment variables

You might want to use Expo Services environment variables if you need to:

  • Keep configuration in one place for cloud builds, updates, and workflows without committing .env files.
  • Separate values by environment (development, preview, production) while reusing names.
  • Control visibility (plain text, sensitive, secret) so only the right surfaces can read each value.
  • Apply the same set locally with eas env:pull or inside CI/CD.

These are the problems that Expo Services environment variables are built to solve. With Expo Services environment variables, the variables are configured in Expo Services via the EAS CLI or directly on the expo.dev dashboard, and can be accessed by Expo Build and Expo Workflows as well as your local machine via the EAS CLI.

Key concepts

Available environments

By default, Expo Services supports three environments for environment variables: development, preview, and production environments. Custom environment names are available on Enterprise and Production plans.

Each environment is an independent set of variables that can be used to customize your app in different contexts. For example, you can use different API keys for development and production, or use different bundle identifiers for app store releases.

Every Expo Build and Workflows job runs using environment variables from one of the available environments. You can also use environments for updates, allowing you to use the same set of environment variables for your build jobs. When publishing an update, specify the environment with the required --environment flag.

Environment variables can be assigned to multiple environments and have the same value across all of them, or be created for a single environment.

Scope

  • Project-wide: Specific to a single Expo Services project. You can create, view, and manage them by navigating to the Environment variables page in your project's dashboard. These environment variables are available in any jobs that run on Expo servers and updates for this project. They can also be pulled locally for development if their visibility setting allows it.
  • Account-wide: Available across all projects in your Expo account. You can create, view, and manage them by navigating to the Environment variables page in your account's dashboard. These environment variables are available in jobs that run on Expo servers and updates, together with project-wide variables for a project. You can pull them locally or read outside of Expo servers if their visibility setting allows it.

Variable types

  • Strings: Standard key/value pairs that can be used across builds, updates, workflows, and hosting.
  • Files: Values uploaded as files (for example, google-services.json or a certificate) that are made available to jobs as file paths on the build runner.

Visibility settings for environment variables

There are three different visibility settings available for each environment variable:

Visibility Description
Plain text Visible on the website, in EAS CLI, and in logs.
Sensitive Obfuscated in Expo Build and Workflows job logs. You can use a toggle to make them visible on the website. They are also readable in EAS CLI.
Secret Not readable outside of the Expo servers, including on the website and in EAS CLI. They are obfuscated in Expo Build and Workflows job logs.

warning Note that anything that is included in your client-side code should be considered public and readable to any individual that can run your app.

warning Secret type environment variables are intended to provide values to an Expo Build or Workflows job so that they may be used to alter how a job runs. For example, setting an NPM_TOKEN to install private packages from npm. Secrets do not provide any additional security for values that you end up embedding in your application itself.
