Each migration is its own folder inside migrations/app/, and the file you edit in it is migration.ts. app is the fixed name of the folder that holds your project's migrations; extension packages that ship their own migrations get folders of their own next to it.

In Prisma ORM 8, schema.prisma is now contract.prisma, your contract: the same language and the same models. npx prisma migration plan writes migration.ts from a change to the contract, and saves a frozen copy of the contract for the migration to point at; when this page says a migration's start or end contract, it means one of those copies. You edit migration.ts, then run it with Node.js, and it writes ops.json, the SQL that will run, next to itself. npx prisma db migrate applies ops.json to the database.

This page lists everything migration.ts can call. For the editing workflow, with a worked backfill, read Editing a migration.

On PostgreSQL, everything comes from one module:

migration plan writes the import line with only the names the migration needs. When you add a call by hand, add its name to the import line. Where a migration holds SQL from your contract, such as a default, a check or an index expression, migration plan writes it as a sql value, as in fn(sql`clock_timestamp()`), imported from the same module. Every call that takes SQL accepts either a sql value or a plain string. A string is used exactly as written, while a sql value has its shared indentation and the blank lines at its start and end removed, so leave the strings in a migration you already applied as they are. On MongoDB the module is @prisma/orm-mongo/target/migration; the path really does contain target, and it is not a placeholder. See MongoDB operations.

The migration file

migration.ts exports one class that extends Migration. This is what migration plan writes for a migration that adds one column:

The four imports at the top point at snapshots, which are copies of your contract that migration plan saves under migrations/snapshots/<hash>/: one for the contract the migration starts from and one for the contract it ends at. You never type those paths; migration plan writes them. codecRef on the column names how its values are read and written; leave it as migration plan wrote it. The last line is what makes the file runnable with Node.js; keep it as written.

Member What it is
Migration<Start, End> The base class. Start and End are the two snapshots' types.
startContractJson The start snapshot's contract.json.
endContractJson The end snapshot's contract.json.
operations The list of changes. They run in the order you list them, table changes and data changes alike, so a dataTransform between two column changes runs between them. Each entry is one call to a method or helper on this page. Return the list as it is; do not await the calls.
this.endContract A read-only view of the end contract, for looking up names and settings in your own code. this.endContract.namespace.public.table.user is the user table in the public schema (namespace in that path means the PostgreSQL schema).
this.startContract The same for the start contract, or null on a first migration.

A first migration starts from an empty database, so it has no start snapshot. migration plan writes it as extends Migration<never, End>, without the two Start imports and without startContractJson.

Running the file turns operations into ops.json, and also writes migration.json, which records the start and end contracts. Every Node.js version Prisma ORM supports (22.18 or newer on the 22 line, 24.11 or newer on the 24 line, or 26 or newer) runs the .ts file directly, with no build step. It reads the prisma.config.ts that owns the migration, to learn which database and extensions the project uses: the nearest one above the migration's directory whose migrations directory holds the file, else the one in the working directory, or the one you pass with --config. It never connects to a database.

Flag What it does
--dry-run Prints migration.json and ops.json to the terminal instead of writing them.
--config <path> Reads that config file instead of ./prisma.config.ts.
--help Prints the flags.

Any other flag fails with an error whose code is CLI.UNKNOWN_FLAG.

Operation classes and checks

Every operation carries an operationClass, which says what kind of change it makes. The methods below set it for you, and rawSql asks you for it. The class changes nothing about what runs: npx prisma db migrate applies every class, and marks each destructive operation with ⚠ and a data-loss warning.

Class Meaning Example
additive Adds something new Add a column, create an index
widening Loosens a rule, or renames something without losing anything Drop NOT NULL, rename an index
destructive Removes or changes something that exists, and can lose data Drop a column, change a column's type
data Changes rows, not tables A dataTransform

Most operations also carry two check queries, a precheck and a postcheck, and db migrate runs them in this order:

  1. The postcheck, which asks "is the change already there?". If it passes, the operation is skipped. This is what lets you run db migrate again after a run stopped partway: what already landed is skipped.
  2. The precheck, which asks "is the database in the state this change expects?". If it fails, the run stops.
  3. The statements.
  4. The postcheck again. If it fails now, the run stops.

The methods below write both checks for you; you write them yourself only in rawSql. How migrations work has the full rule.

PostgreSQL operations

Each operation is a method you call on the migration, this.<name>({ ... }), with one options object. Every method takes schema; a schema? in the tables below means you may leave it out. For createSchema, renameSchema and dropSchema it is the schema to create, rename or drop. For every other method it is the PostgreSQL schema the table is in, which is public unless your contract sets another. Names are quoted for you: pass user, not "user". Pass the table name, which is the model name exactly as written, such as User, unless the model sets @@map: a model with @@map("user") has the table user. Runs is the SQL for this page's example names.

Schemas and tables

Method Options Runs Class
createSchema schema CREATE SCHEMA IF NOT EXISTS "app" additive
createTable schema, table, columns, constraints? CREATE TABLE "public"."post" (...) additive
renameTable schema?, table, to ALTER TABLE "public"."userProfile" RENAME TO "UserProfile" widening
dropTable schema, table DROP TABLE "public"."post" destructive
renameSchema schema, to ALTER SCHEMA "billing" RENAME TO "finance" widening
setTableSchema schema?, table, to ALTER TABLE "public"."invoice" SET SCHEMA "billing" widening
dropSchema schema DROP SCHEMA "billing" widening

columns is a list of col(...) calls and constraints a list of primaryKey(...), unique(...), foreignKey(...), and checkExpression(...) calls, all rendered inside the CREATE TABLE statement. That section shows a full createTable call and the SQL it produces.

renameTable renames a table and keeps its rows. It also renames each primary key, unique constraint, foreign key, index and check whose name migration plan derived from the old table name, so it returns a list of operations: spread it into the list, as in ...this.renameTable({ table: 'userProfile', to: 'UserProfile' }). It reads the names from the migration's start and end contracts. Change the table name in your contract (the model name, or its @@map), and run prisma contract emit. migration plan plans the change as a dropped table and a new one: replace that pair with the renameTable call, or write the call in an empty migration from prisma migration new. Pass schema only when more than one schema has a table of that name. When the start contract has no such table, or the end contract has no table named to, it fails with MIGRATION.TABLE_RENAME_UNMATCHED. On SQLite, renameTable takes table and to.

renameSchema renames a schema, and everything in it stays in it. setTableSchema moves a table to the schema to, with its rows, constraints, indexes and policies; foreign keys from other tables keep pointing at it. Leave out schema for a table that is in no schema. Later renameTable and renameColumn calls in the same migration find the table under its new schema or schema name. dropSchema drops a schema without CASCADE, so drop or move its tables first: its precheck fails while the schema still holds a table, view, sequence, type or function. migration plan writes these calls when you pass --rename billing:finance, --rename public.Invoice:billing.Invoice or --delete billing. They are PostgreSQL only.

Columns

Method Options Runs Class
addColumn schema, table, column ALTER TABLE "public"."user" ADD COLUMN "bio" text additive
dropColumn schema, table, column ALTER TABLE "public"."user" DROP COLUMN "bio" destructive
alterColumnType schema, table, column, type, using?, raw?, operationClass? ALTER TABLE "public"."post" ALTER COLUMN "views" TYPE bigint destructive, or data with using
setNotNull schema, table, column ALTER TABLE "public"."post" ALTER COLUMN "views" SET NOT NULL widening
dropNotNull schema, table, column ALTER TABLE "public"."post" ALTER COLUMN "views" DROP NOT NULL widening
setDefault schema, table, column ALTER TABLE "public"."user" ALTER COLUMN "name" SET DEFAULT 'anonymous' additive, or widening when the column already has a default
dropDefault schema, table, column ALTER TABLE "public"."user" ALTER COLUMN "name" DROP DEFAULT widening

addColumn and setDefault take a col(...) call as column. The other methods take the column's name as a string.

alterColumnType takes the new type in type, written the way a migration writes it, such as 'int8', 'varchar(255)', or '"Mood"' for an enum. Prisma ORM recognizes the PostgreSQL types it supports and the types of the extension packages in your configuration, and after the change db migrate checks that the column has the type you wrote. A type it does not recognize fails with MIGRATION.COLUMN_TYPE_UNREADABLE. If that type comes from an extension package, add the package to your configuration. For any other type, set raw: true and pass the type exactly as PostgreSQL prints it, because db migrate then compares the column's type with that text.

using is the expression in the USING clause, for a conversion PostgreSQL cannot do on its own. Without it, the column is cast to the new type. Write it as SQL over the column, such as '"views"::bigint'. A semicolon, a SQL comment or dollar quoting outside a quoted literal, or a comma or a keyword such as FROM outside parentheses, fails with MIGRATION.SQL_EXPRESSION_INVALID. The operation is data when it has a using, and destructive otherwise; pass operationClass ('widening', 'destructive', or 'data') to choose another class.

When the column is an autoincrement() column, alterColumnType also changes the sequence the column owns to the new width, with ALTER SEQUENCE ... AS bigint for an int8 column. It first refuses, before any statement runs, when the sequence has already handed out a value too large for the new width. A migration applied before 8.0.0-rc.19 left the sequence at its old width. Change it yourself, for example ALTER SEQUENCE "public"."post_id_seq" AS bigint; pg_get_serial_sequence('"public"."post"', 'id') names the sequence.

A using needs a type change. If the new type is the type the column already has in the contract the migration starts from, migration.ts refuses the alterColumnType with MIGRATION.ALTER_COLUMN_TYPE_USING_WITHOUT_TYPE_CHANGE, because db migrate would find that the column already has that type and skip the operation, so the conversion would never run. To change the values in a column and keep its type, write a dataTransform instead, which checks the rows themselves.

A migration.ts written before 8.0.0-rc.18 passed an options object with qualifiedTargetType, formatTypeExpected and rawTargetTypeForLabel. It now stops with MIGRATION.OPERATION_OPTION_REMOVED: move qualifiedTargetType to type and options.using to using, and delete the other two. If no database has applied the migration yet, run it again to write ops.json; if one has, leave ops.json and migration.json as they are, because writing them again changes the migration's hash.

setDefault takes the column with its new default, and Prisma ORM writes the DEFAULT clause: column: col('name', 'text', { default: lit('anonymous'), codecRef: { codecId: 'pg/text@1' } }), or column: col('createdAt', 'timestamptz', { default: fn('now()') }). When you pass a codecRef, Prisma ORM first checks that a literal default is a valid value of that type, and a value that is not fails with CONTRACT.DEFAULT_INVALID.

setDefault has no postcheck, so it always runs, which means it can also replace a default the column already has. After the last operation, db migrate checks that the default matches your contract. The operation is widening when the column already has a default in the contract the migration starts from, and additive otherwise.

setDefault takes no operationClass; a call that still passes one runs and ignores it. A migration.ts written before 8.0.0-rc.15 that still passes defaultSql stops with MIGRATION.OPERATION_OPTION_REMOVED, so rewrite the call as shown above. Its existing ops.json still applies.

setNotNull has an extra precheck that fails while the column still holds a NULL, so backfill the column with a dataTransform first. Editing a migration shows the three steps.

Method Options Runs Class

addUnique schema, table, constraint, columns ALTER TABLE "public"."user" ADD CONSTRAINT "user_name_key" UNIQUE ("name") additive

addCheckConstraint schema, table, constraint, expression ALTER TABLE "public"."post" ADD CONSTRAINT "post_title_len" CHECK (length("title") > 0) additive
renameCheckConstraint schema, table, from, to ALTER TABLE "public"."post" RENAME CONSTRAINT "post_title_len" TO "post_title_nonempty" widening
renameConstraint schema?, table, kind, from, to ALTER TABLE "public"."user" RENAME CONSTRAINT "user_pkey" TO "account_pkey" widening

In these calls, constraint is the name to give the constraint, or the name of the one to drop, and columns is the list of column names it covers:

foreignKey is an object: name, columns (on this table), references with its own schema, table, and columns, and optional onDelete and onUpdate, each one of 'noAction', 'restrict', 'cascade', 'setNull', or 'setDefault':

renameConstraint renames a constraint of any kind: 'primaryKey', 'unique', 'foreignKey', or 'checkConstraint'. renameCheckConstraint is the same call with kind: 'checkConstraint'.

dropConstraint removes a primary key, unique, or foreign key constraint by name. Pass its kind as kind, one of 'primaryKey', 'unique', or 'foreignKey'. kind is recorded in ops.json for reporting only and does not change the SQL; it defaults to 'unique'. A check constraint has its own dropCheckConstraint.

addCheckConstraint adds a check to a table that already exists; checkExpression(...), listed under helpers, is the same thing inside a createTable. In both, expression is SQL and goes into the statement as you wrote it, so quote column names yourself: 'length("title") > 0'.

There is no method that renames a column. Raw SQL shows a column rename. To rename a table, use renameTable.

It has no precheck or postcheck, so if a db migrate run stops partway and you run it again, this operation runs again, which is harmless because of IF NOT EXISTS.

installExtension is for the older migrations of an extension package that ships its own migrations, and there extensionName, invariantId, and id are all required. Call Arguments Class
this.dataTransform(contract, name, options) endContract, the contract object built below; a name for the operation; and options with run, check?, and invariantId? data

run is a callback that returns an update built with the SQL query builder, or a list of such callbacks that run in order. check is a callback that returns a query for the rows still needing the change. You write that one query; the precheck passes while it finds rows, and the postcheck passes once it finds none.

Both callbacks build their queries with db, a query builder, and db needs a contract object built from the end snapshot's JSON. migration plan does not write those lines; you add them whenever a migration has a dataTransform. migration plan writes a dataTransform with placeholder('<name>:check') and placeholder('<name>:run') in the two positions for each field you name with --backfill <Model.field>, and an alterColumnType with using: placeholder('<Model.field>:convert') for each field you name with --convert; you replace each placeholder(...) call with a query or a conversion. Raw SQL

Call Argument Class
rawSql(operation) an operation object you write in full the operationClass you set

rawSql is not a method: import it from @prisma/orm-postgres/migration and call it without this., as the example below does. Use it for a statement that has no method on this page, such as a column rename or COMMENT ON. db migrate checks the database against the end contract after applying a migration, so a raw change has to match a change in your contract: to rename a column, rename the field in contract.prisma, run migration plan, and replace the dropColumn and addColumn it writes with one rawSql. Pass it an object with these fields:

Field What it is
id A name for the operation, used in error messages. Any string; keep it unique within the migration. The planner's own look like index.post.post_author_idx.
label The text the CLI prints while applying it.
operationClass One of the four classes.
target Always { id: 'postgres' }.
precheck, execute, postcheck Lists of steps, each { description, sql, params? }. A check step can also take expectation. execute holds the statements; the other two hold the checks, described below.

Writing the checks

A step's sql can use $1, $2, and so on, with the values in params. A check passes when its query returns true in the first column of its first row. It fails when the query returns false or no rows.

Write the precheck so that true means "go ahead", as in "column bio exists" above. Write the postcheck so that true means "the change is there", as in "column biography exists". Remember the order: the postcheck runs first, and if it already passes the operation is skipped. An empty precheck always lets the statements run. An empty postcheck never passes beforehand, so the operation runs on every db migrate that reaches it, including a second run after a failure.

A check that asks whether one object exists can say so in expectation: { expects: 'absent' | 'present', object }, where object names the object as a reader would, such as 'column "biography" on "user"'. When the check fails, the error then says what the database already has or lacks, such as the database already has column "biography" on "user", in place of That check failed on this database. object is only display text. Leave expectation out of a check about data or about several objects at once, such as a check that a column holds no NULL values. Add it only to a migration no database has applied yet. Then run node migration.ts again, which rewrites ops.json and migration.json.

A call without name uses the name after the keys and their directions, such as email_1, so a migration.ts written before index names were recorded keeps working.
