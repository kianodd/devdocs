With socket activation, the service manager opens the listening socket for your application. systemd listens on the port, starts the application when the first connection arrives, and hands the socket over to it. Connections that arrive while the application starts or restarts wait in the kernel's queue instead of being refused.

This is useful for services that are called rarely, such as internal tools, admin panels, or the many services of a development or staging machine. If the application also exits after some time without requests, such a service holds no memory while nobody uses it. The cost is a cold start: the first request after a pause waits until Node.js loads the application and Nest bootstraps it.

Hint

Listening on a socket passed by the service manager is a feature of Node.js's server.listen(). It is not supported on Windows.

Warning

Start node directly in ExecStart. systemd passes the socket as file descriptor 3 and sets the LISTEN_FDS and LISTEN_PID environment variables, where LISTEN_PID is the ID of the process it started. With npm start, nest start, or a shell script in between, LISTEN_PID doesn't match your application's process. The bootstrap below then falls back to listening on the port, which fails with EADDRINUSE because systemd already holds it.

Hint

To try it without unit files, run systemd-socket-activate --listen=3000 node dist/main.js. It passes the socket the same way, but starts the application only once. It also doesn't forward variables such as NODE_ENV unless you name them with --setenv=NODE_ENV.

app.close() runs the same shutdown hooks as enableShutdownHooks() does when systemd stops the service with SIGTERM. Exit code 0 tells systemd that the service stopped cleanly, so Restart=on-failure doesn't start it again. systemd keeps its own copy of the socket open, so a connection that arrives while the application exits waits for the next start.

The helper counts HTTP requests only. A server-sent events stream counts until the client disconnects, but an open WebSocket connection doesn't. If your application uses WebSockets, also count the sockets of the server's upgrade event until they close.

Things to keep in mind

  • Use Restart=on-failure, not Restart=always. With always, systemd starts the application again right after it exits on idle.
  • Health checks and uptime monitors that send requests to the application start it and keep it running.
  • Scheduled jobs (see Task scheduling) and queue consumers don't run while the application is stopped. Run them in a process that stays up.
  • The first request after a pause waits for the whole bootstrap, including database connections opened by async providers. The Serverless chapter shows ways to shorten it. Node.js can also reuse its compile cache between starts: add Environment=NODE_COMPILE_CACHE=/var/cache/my-app and CacheDirectory=my-app to the service unit. Node.js writes the cache when the process exits, and a process killed by SIGTERM without enableShutdownHooks() doesn't write it.
