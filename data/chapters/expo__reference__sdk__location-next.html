info The next version of the Location API is included in the expo-location library. It can be used alongside the previous API. Since it is in beta, the API might change between SDK versions.

expo-location/next reads the device's location once, watches it while the app is open, and receives it in the background. On Android, it also lets you pick the location provider.

Installation

Usage

By default, a permission request asks for the precise location. On Android, this requests both ACCESS_COARSE_LOCATION and ACCESS_FINE_LOCATION; when the user has already granted the approximate location, the dialog asks to change it to the precise one. On iOS, when the user has turned Precise Location off for the app, the request also shows the system prompt for temporary full accuracy.

The iOS prompt shows a default message, which the locationFullAccuracyPermission config plugin option can replace.

An approximate location is accurate to kilometers rather than meters. To get it, request the permission with accuracy: RequestPermissionsAccuracyOption.REDUCED.

On Android, this requests only ACCESS_COARSE_LOCATION, so the permission dialog does not offer the precise location.

On iOS, the app does not ask to upgrade to the precise location. To make the approximate location the default in the permission dialog, set isIosReducedAccuracyByDefault to true in the config plugin. getPosition resolves with a single fix. It returns a cached fix when one is younger than maxCachedAge. Otherwise, it waits up to timeout seconds for a new one and falls back to the last known location when none arrives. Both values are in seconds. Check timestamp when freshness matters.

When timeout is set to 0, the call resolves immediately with the last known position, without asking for a new fix.

When the user denies the permission, canAskAgain tells whether the system shows the dialog again. When it is false, the only way to grant the permission is the system settings, so send the user there.

On Android, the background permission requires the foreground permission first. The request throws when the foreground permission is not granted. Receiving positions in the background also needs the background permission declared on Android and the background mode on iOS. Enable both in the config plugin:

On Android 11 and later, the system opens the app's settings page instead of a dialog. The request resolves when the user comes back.

isAndroidBackgroundLocationEnabled adds five permissions: ACCESS_BACKGROUND_LOCATION, RECEIVE_BOOT_COMPLETED, FOREGROUND_SERVICE, FOREGROUND_SERVICE_LOCATION, and POST_NOTIFICATIONS. The last three are for the location foreground service; set isAndroidForegroundServiceEnabled to false to leave them out.

On iOS, the request shows the Change to Always Allow dialog. Answering Keep Only While Using resolves with status: "denied" and scope: "whenInUse", because the foreground permission stays granted.

watchPosition returns a handle that controls the native watcher. Pause it when the screen loses focus, resume it when the screen is back, and dispose it when the screen unmounts. A screen that loses focus stays mounted behind another tab, a pushed screen, or a modal. On Android, the watcher also pauses on its own while the app is in the background, unless a location foreground service is running.

Location services are a device-wide switch, separate from the app's permission. With services off, no app receives a position. On Android, enableLocationServices asks the user to turn them on: Google Play services shows an in-app prompt, and the Android provider opens the system settings. Both require the app to be in the foreground with a current Activity. On iOS, only the user can turn them on in Settings.

To receive positions while the app is in the background, define a task with defineLocationTask at the top level of a module. Then start the delivery with LocationUpdatesHandle. This requires expo-task-manager, the background permission, ACCESS_BACKGROUND_LOCATION and RECEIVE_BOOT_COMPLETED declared on Android, and the location background mode on iOS. On Android, a profile means something different for a background task than for a watcher. LOW_POWER waits much longer between positions, batches them, and skips positions close to the last one, so a device that stays put may produce none. AUTOMOTIVE_NAVIGATION delivers as often as the system allows, with no batching and no distance filter.

Both sides default to the same task name, so you can omit it. To run several tasks, give each task its own name and pass that name to both defineLocationTask and the LocationUpdatesHandle constructor.

On Android 8 and later, while the app is backgrounded, the watchers stop and location tasks trigger rarely. If you want a steady stream of position fixes in the background, start a background session with ensureBackgroundSessionStarted. The session runs as a location foreground service with a notification. You can start it only while the app is in the foreground. It needs the FOREGROUND_SERVICE and FOREGROUND_SERVICE_LOCATION permissions, so set isAndroidForegroundServiceEnabled to true in the config plugin.

The call to ensureBackgroundSessionStarted persists the configuration passed to it. With the configuration present, the module restarts the background session whenever the app enters the foreground, even after the app is closed and reopened.

If you no longer need the background session, you need to manually stop it using stopBackgroundSession.

API

Permissions

Android

Installing expo-location adds ACCESS_COARSE_LOCATION and ACCESS_FINE_LOCATION.

The config plugin adds the rest when isAndroidBackgroundLocationEnabled is true. Enabling ACCESS_BACKGROUND_LOCATION or the location foreground service in a new build requires submitting the app for review. See Google Play's requirements for background location permissions and foreground services.
