Middleware lets you run your own code around every query your app sends through Prisma ORM.

For example, you can log every query with its latency, block a DELETE that has no WHERE clause before it reaches the database, or serve a repeated read from memory instead of running it again. You write the policy once, register it once, and every query follows it, with no call sites to update.

If you used $use in Prisma ORM 7, the middleware array is its replacement. There is no next(): you pick the hook that runs at the moment you care about. Coming from Prisma ORM 7 lists Prisma ORM 7 features next to the Prisma ORM 8 form each one takes.

A middleware is a plain object with a name and one or more hooks, and a hook is a function that Prisma ORM calls at a fixed moment around a statement or a transaction. You register the whole object once, in the middleware option of your client setup.

If you set your project up by hand, The data contract covers where they come from.

The name is the label Prisma ORM uses when it has to say which middleware it means in an error message, and nothing requires it to be unique. familyId: 'sql' means this middleware works with SQL databases only, so Prisma ORM rejects it on a MongoDB client.

Add queryLogger() to the middleware array in src/prisma/db.ts, alongside the built-in middleware or on its own, and every query on that client runs through it. The authoring guide builds this logger step by step, with the options and the other hooks.

Every query goes through that list, whichever of the two APIs you wrote it with. With the ORM API you write db.orm.public.User..., where public is the PostgreSQL schema and User is the model in your contract.

With the SQL query builder you build a query and run it in two steps. .build() returns a plan, which is the query as a plain object, not yet run. db.query(plan) runs it and returns rows, and db.execute(plan) runs it and returns how many rows it changed.

Both APIs send their queries on the same db object, so both see the same middleware. If your database is MongoDB, pass the same middleware option to mongo(...) from @prisma/orm-mongo/runtime and type your own middleware as MongoMiddleware from @prisma/orm-mongo/family-runtime.

When your hooks run [#the-two-lifecycles]

You write only the hooks you care about, and Prisma ORM skips the ones you leave out. Prisma ORM sends statements, runs the transactions you open with db.transaction(...), and on SQL databases runs ORM calls. Each statement, transaction or ORM call is an activity. A middleware sees each activity through lifecycle hooks and interceptors:

  • Lifecycle hooks observe. activityStarted, activityEnded and activityFinalized run for every activity, a statement, a transaction or an ORM call, in that order.
  • Interceptors change or stop a statement while it runs: beforeCompile, beforeEncode, intercept.onQuery or intercept.onExecute, and onRow. One more interceptor, intercept.onActivity, can answer a whole ORM call.

A statement calls your hooks in this order:

activityStarted → beforeCompile → beforeEncode → intercept.onQuery or intercept.onExecute → onRow (once per row) → activityEnded → activityFinalized

The same order holds for a statement that returns rows and one that only reports how many rows it changed. activity.returns on the statement tells them apart:

  • 'stats': a statement that reports only how many rows it changed. db.execute(plan) sends one, and so do the ORM methods createAndCount, updateAndCount and deleteAndCount, and a nested write that links or unlinks rows of a many-to-many relation.
  • 'rows': every other statement, including those sent by db.query(plan).

intercept.onQuery runs only for 'rows' and intercept.onExecute only for 'stats', and onRow runs only when rows come back. If those names are new, the queries table puts each of them next to the Prisma ORM 7 call it replaces.

A transaction runs only the three lifecycle hooks: activityStarted when it opens, activityEnded when its commit() or rollback() settles, and activityFinalized after that. A statement sent inside db.transaction(...) is beneath the transaction, so ctx.inTransaction() is true in its hooks. ctx.parent is the context of the activity directly above it: the transaction, or the ORM call that sent the statement.

ORM calls [#orm-calls]

On a SQL database, each ORM method that runs a query, such as .all(), .first(), .create(), .updateAll() or .aggregate(...), runs as one activity whose activity.kind is 'orm-call'. Each run of a prepared statement built from an ORM query is one too. The SQL query builder's db.query(plan) and db.execute(plan) are not ORM calls: they send one statement, which is its own activity.

  • It opens when the call starts, before it sends anything. For .all(), that is when your code starts reading the rows, with await or for await.
  • The statements it sends are beneath it. A nested create, for example, sends several statements, and all of them are children of the one call. A call that needs a transaction of its own opens it beneath the call. A call made inside db.transaction(...) is a child of that transaction.
  • It ends when the call has its result, or fails. For .all() read with for await, it ends when your code reads the last row, stops early, or the read fails.
  • It carries activity.id, activity.annotations and activity.contentHash(). The annotations are the ones you attached with meta.annotate(...), and the statements the call sends carry none of them, so read them in activityStarted from the orm-call activity. An ORM call has no plan and no returns.

Use activity.contentHash() when you need a key for an ORM read, for example to cache it: the cache uses it for an annotated ORM read that has no key. It returns a promise of a digest of the call. For a read, the digest covers the method and the first statement the call sends, with its parameter values. For a write, it covers only the method and the model, because a write's statements depend on the results of earlier ones. So two writes to the same model get the same digest.

A call runs activityStarted, then intercept.onActivity, then the hooks of each statement it sends, then activityEnded and activityFinalized. In activityEnded:

  • result.kind is 'orm-call'.
  • result.outcome is 'succeeded', 'failed' or 'stopped'.
  • result.source is 'client', or 'middleware' when intercept.onActivity answered the call.
  • result.result is the value the method returns. A call that streams rows, such as .all(), keeps them in result.result only when it carries an annotation, so an unannotated read does not hold all its rows in memory.
  • There is no latencyMs. To time a call, keep ctx.now() in ctx.state(key) in activityStarted.

Outside a transaction, the call is finalized right after it ends: its activityFinalized hooks run, once its effects are final. The outcome is 'committed' when the call succeeded and everything beneath it was finalized 'committed', otherwise 'unknown'.

The order your middleware runs in

Prisma ORM calls your middleware in the order you listed them in the middleware array, at every hook, so the middleware at index 0 goes first. If one middleware rewrites the query in beforeCompile, the one after it sees the rewritten version. The lifecycle hooks follow that same order rather than unwinding in reverse, so the middleware at index 0 is also the first to log. Order decides who answers a statement as well: when several middleware implement intercept.onQuery, the first one that returns rows wins and the rest are not called at all, and the same holds for intercept.onExecute and intercept.onActivity.

activityStarted: the activity begins

activityStarted(activity, ctx) runs first, before anything is compiled or sent. activity.kind is 'statement', 'transaction' or 'orm-call', activity.id is a fresh id that every hook of the activity sees, and for a statement activity.plan is the plan the caller sent and activity.returns is 'rows' or 'stats'. Throwing from it fails the activity, and the middleware listed after it never see the activity at all.

beforeCompile: rewrite the query

Reach for beforeCompile when you want to change what a query asks for rather than only look at it. It hands you a draft with two fields: meta, facts about the query that you read but do not change, such as which API built it, and ast, the query as a tree of typed objects. The tree is the part you can change, because the SQL text has not been written yet. Return a copy of the draft with a changed ast and Prisma ORM runs your version instead, which is how you add a condition to queries without editing a single call site. Return undefined and the query goes through as written.

beforeEncode: validate or block

beforeEncode is where you inspect a statement and refuse it. It runs after the SQL text has been written out and before the parameter values are encoded and anything reaches the database, for statements of both kinds. Your hook receives the plan, so you can read the SQL text in plan.sql and read the same query as objects in plan.ast, which is the tree beforeCompile works on. Throwing from the hook blocks the statement, and returning normally lets it carry on to the database:

This is where lints stops a DELETE without WHERE, and where budgets rejects a query that would read too many rows.

Every hook also receives a context object, ctx, which tells it about the activity it is running inside. ctx is the argument after plan, or after result in activityEnded and activityFinalized. ctx.state(key) returns an object that belongs to this one activity, so a value your beforeEncode stores there is still there in your activityEnded. ctx.scope is 'transaction' for a statement inside db.transaction(...) and 'runtime' for one you sent on db directly, so your middleware does see the statements you run in a transaction. The context object lists every field it holds.

The hook can also change the values the statement sends to the database, and it does that through a third argument, params, which you declare as beforeEncode(plan, ctx, params) when you want it. params.entries() walks those values one at a time, and each entry has three fields:

  • entry.value is the value itself.
  • entry.codecId is the stored type, an id such as pg/text@1, pg/int4@1, or pg/timestamptz-date@1.
  • entry.ref identifies that one value in the query, and it is what you pass to replaceValue.

Call params.replaceValue(entry.ref, newValue) and the database receives your value instead of the original. params is typed as optional and Prisma ORM always passes it, so the guard on the first line is there to satisfy TypeScript:

intercept: answer without the database

intercept.onQuery and intercept.onExecute let you answer a statement yourself, so the database never sees it. They go in an intercept object on your middleware. Return { rows } from onQuery, or { stats } from onExecute, and that is what your caller gets back, but return undefined and the statement carries on to the database as usual. The stats you return is the count that statement reports, for example { stats: { affectedRows: 0 } }:

The rows you return are plain objects, keyed by the column aliases in the SQL, holding the values in the form the database driver hands them over. On PostgreSQL every value that is not SQL NULL is the text the database printed, so integers are strings, as are text and timestamps. A NULL stays null. So for a query whose SQL is SELECT "User"."id" AS "id", "User"."email" AS "email" FROM "public"."User" LIMIT 5, return { rows: [{ id: '1', email: 'mia@prisma.io' }] } is a complete answer to it. Prisma ORM converts the rows you return the same way it converts rows from the database. So if you return a createdAt as a string, a caller on the ORM API gets a Date, which is the type of a DateTime field.

intercept.onActivity(activity, ctx) answers a whole ORM call instead of one statement. It runs after the call's activityStarted hooks and before the call sends anything. Return { result }, where result is the value the method returns, and the call sends no statement at all. This is how the cache serves an annotated ORM read. Answer ORM calls with intercept.onActivity shows an example.

beforeEncode still runs on a statement that intercept.onQuery or intercept.onExecute answers, because every middleware's beforeEncode runs before any of those handlers, whatever order you list the middleware in. So in the setup at the top of this page, where the cache comes first in the array, lints still checks a SQL builder query before the cache answers it. An ORM call that intercept.onActivity answers is different: it builds no statement, so no beforeCompile, beforeEncode or onRow hook runs for it, and lints does not see an ORM read the cache serves. A check that must also cover those reads belongs in activityStarted, which runs before intercept.onActivity.

onRow: watch rows arrive

onRow(row, plan, ctx) lets you see each row of a result on its way to your code, and row is one of those plain row objects. Prisma ORM calls it once for every row as it reads the result, before your await on .all() or .first() resolves, so you can count rows, sample them, or throw to stop the query part way through. If you throw, your await rejects with that error and you get no rows at all, not the rows read so far. That is what budgets does when a query returns more rows than its maxRows budget allows. onRow does not run on a statement that returns no rows, and it does not run for rows that an intercept handler answered.

activityEnded: observe the finished activity

activityEnded(activity, result, ctx) is for recording what happened once the work is over. Prisma ORM calls it once at the end of every activity, whether it succeeded or failed, so check result.kind first if you only care about statements.

For a statement, result.outcome is 'succeeded', 'failed', or 'stopped' when your code stopped reading the rows part way through. result.latencyMs is how long it took, and result.source is 'driver' for a statement the database answered and 'middleware' when an intercept handler answered it. result.returns says which of the two counts is there: result.rowCount, how many rows came back, when it is 'rows', or result.stats.affectedRows, how many rows the statement changed, when it is 'stats'. There is no result.stats on a write that failed.

A statement that fails before it reaches the database, in beforeCompile, beforeEncode or while its values are encoded, also ends, with outcome: 'failed', latencyMs: 0 and source: 'driver'. A middleware that counts statements or measures latency checks result.outcome to leave those out.

For a transaction, result.outcome is 'succeeded' when its commit() or rollback() resolved and 'failed' when it rejected, so a transaction that rolled back as you asked ends 'succeeded'.

Timing, logging, and latency budgets all belong in this hook. The SQL text is not on the activity; when you want to log it, keep it from beforeEncode in ctx.state(key), as Authoring custom middleware shows.

activityFinalized: act once the effects are final

activityFinalized(activity, result, ctx) is the last hook of every activity. It runs once, when the activity's effects are final. For a statement inside db.transaction(...), that is after the transaction commits or rolls back, so each statement of the transaction gets its call then, not when the statement itself finished. The statements are finalized first, in the order they started, then the transaction itself. For a statement outside a transaction, it runs right after activityEnded.

result.outcome says what happened: 'committed' when the transaction committed, or the statement outside a transaction succeeded; 'rolled-back' when the transaction rolled back; and 'unknown' when Prisma ORM cannot tell whether the writes landed, for example when a statement outside a transaction failed, or a statement inside a committed transaction failed. Use this hook for work that must not happen for a write that did not last, such as publishing an event or removing a cache entry, and treat 'unknown' like 'committed' when a committed write must not be missed. Check activity.kind === 'statement' if you act on statements only, because transactions and ORM calls are finalized too.

Inside a transaction, the hooks run while the transaction's connection is still checked out, so keep them short. Do not send a query on that connection, and do not wait on another query through the same client: if every connection of the pool is busy, it never finishes. Prisma ORM passes an error thrown from activityFinalized to the client's log and does not pass it to your code. Give the client a log option, such as log: console, to see it.

Which databases a middleware runs on

Prisma ORM sorts the databases it supports into two families, SQL and MongoDB, and a middleware cannot always work on both. The familyId key next to name is where a middleware says which family it was written for, and a middleware that leaves familyId out runs on either.

  • budgets and lints declare familyId: 'sql'. They register on PostgreSQL and are rejected on MongoDB.
  • The cache declares no familyId. It never reads SQL, so it runs on PostgreSQL and on MongoDB.

If you register a middleware against a database it was not written for, that client throws at its first query (or at connect(), if you call it), before anything reaches the database. The error's code is RUNTIME.MIDDLEWARE_FAMILY_MISMATCH.

A middleware of your own that leaves familyId out can still be typed as SqlMiddleware, as long as you only ever register it on postgres(...). To write one object that you register on a postgres(...) client and a mongo(...) client both, type it as CrossFamilyMiddleware instead, which you import from @prisma/orm-postgres/components/runtime.

When a middleware or the driver throws

When your hook throws from activityStarted, beforeCompile, beforeEncode, or an intercept handler, the whole statement fails before anything reaches the database, and your caller gets the error you threw. A throw from onRow also fails the statement, but by then the query has run: your caller gets your error and none of the rows, including the ones already read. Your own middleware can throw whatever error you like, as noDeleteAll throws a plain Error. lints and budgets throw an ordinary Error with a code property on it, so you catch them like any other error and read code to tell them apart. budgets throws two codes, BUDGET.ROWS_EXCEEDED and BUDGET.TIME_EXCEEDED, and the lints page lists the codes lints throws.

When the database driver is the thing that fails, Prisma ORM still calls activityEnded on every middleware, with result.outcome set to 'failed', so your logging sees failed statements as well as successful ones. A throw from activityEnded after a statement succeeded fails it, and your caller gets that error; every other middleware still receives its activityEnded. A throw from activityEnded while it is handling a failure cannot hide the real error: your caller still gets the failure the driver reported, and Prisma ORM passes your error to the client's log.
