PSL, the Prisma Schema Language, is the preferred way to author your contract, the contract.prisma file that replaced schema.prisma. You usually write one file, src/prisma/contract.prisma, or split it into several, and npx prisma contract emit writes contract.json and contract.d.ts beside it. If you know the Prisma schema language, most of a contract file reads exactly as you expect. The five biggest additions are listed here, and the rest of the page is the full reference for every attribute and block:

  • mixins: write a set of fields, attributes or enum members once and include it in several blocks.
  • named types: give a database column type a name you can reuse on many fields.
  • enums: an enum can now say how its values are stored, and what each member stores.
  • value objects: a structured value stored inside its parent row, with no table of its own.
  • base models and variants: one table can hold more than one kind of record. Put the shared fields in a base model, put the differences in each variant, and Prisma ORM uses one column to tell them apart.
  • extension types: field types that come from an npm package, such as vectors.

The datasource and generator blocks are gone: the connection URL and the file paths are set in prisma.config.ts instead. Coming from Prisma ORM 7 lists every change to the schema file, including what each old @db. attribute becomes.

A complete contract

The first non-blank line of every contract file is // use prisma-8, because contract emit reads only the .prisma files that start with it. When the contract setting in prisma.config.ts names one file and that file lacks the line, contract emit fails with CONTRACT.SOURCE_LOAD_FAILED, and the error's details include PSL_NO_OPTED_IN_SCHEMA_FILES. When contract is a glob that matches several files, a file without the line is left out of the contract without a warning, and contract emit fails only when none of the files has it.

Uuid is PostgreSQL's uuid type written as a field type. Run npx prisma contract emit after any change to refresh contract.json and contract.d.ts, and then npx prisma db init creates the tables.

Set contract to a glob, such as "./src/prisma/**/*.prisma", to write the contract in several files. Every matching file that starts with // use prisma-8 becomes part of one contract, and a file you add later joins it on the next contract emit, with no change to the config. Models and fields

Models declare fields with a type, an optional ? marker, and attributes. Scalar fields lists the types a field can hold, among them String, Int, Boolean, Decimal, DateTime, Json, and Bytes.

On PostgreSQL, Int, BigInt, Float, Decimal, String, Boolean and Bytes are convenience types, named for what the field means. Each becomes one explicit type, which is named after the database type and sets the column and the kind of value your code reads. Written bare, each gives the type in the first row for it below. For Int, BigInt, Float and String, the storage argument chooses another column. Decimal, Boolean and Bytes have only the one column shown. as chooses what your code reads from a BigInt:

Decimal also takes precision and scale, and String with storage: varchar or storage: char takes length, as in Decimal(precision: 10, scale: 2) and String(storage: varchar, length: 35). Write these three by name, because a positional argument fills storage first: Decimal(10, 2) is refused at storage. String(length: 35) is refused too, because a bare String is a text column, which has no length. The contract stores only the explicit type, so you can also write the explicit type itself, such as Int2, Varchar(35) or NumericString(10, 2).

You can also use one of these PostgreSQL types as the field type: Uuid, Inet, Bit, Varbit, Xml, Oid, Money, or one of the date and time types below. Bit(8) and Varbit(64) set a length, and TimestamptzTemporal(3) or DateTime(precision: 6) sets how many digits of a second are kept. Write each length, precision and scale as a whole number without quotes: Varchar("35") and Varchar(35.0) are refused with PSL_VALUE_TYPE_INCOMPATIBLE. Xml reads and writes text and has no equality, so no filter can compare it. Oid reads a whole number from 0 to 4294967295. Money reads a decimal string with two fraction digits, such as "-1234.56", whatever the database's locale.

The names SmallInt, BigIntNumber, Numeric, UnboundedInt, Real, VarChar and VarBit are deprecated. They still work and give the same contract, but contract emit and the editor report the warning PSL_DEPRECATED_SCALAR_NAME where one is written, and they will be removed. Write the convenience type that gives the same type instead. VarBit has no convenience type, so write the explicit type Varbit:

On PostgreSQL, a date or time field is written with one of four types named for what the field means. Each becomes one explicit type, which names the column and the kind of value your code reads. At their defaults they need no Temporal:

Written Becomes Column Your code reads
DateTime TimestamptzJsDate(3) timestamptz(3) a JavaScript Date
Date DateString date a string, such as "2024-02-29"
Time TimeString time a string, such as "09:30:00"
Duration IntervalString interval an ISO 8601 duration, such as "P1M"

Arguments choose another explicit type. as picks what your code reads: jsDate, string or temporal for DateTime, string or temporal for Date and Time, and string or parts for Duration. storage picks the column: timestamptz or timestamp for DateTime, and time or timetz for Time. precision sets the digits of a second. So DateTime(as: temporal) is TimestamptzTemporal, read as a Temporal.Instant; DateTime(as: string) is TimestamptzString; DateTime(storage: timestamp) is TimestampJsDate(3); Date(as: temporal) is DateTemporal, a Temporal.PlainDate; Time(as: temporal) is TimeTemporal, a Temporal.PlainTime; Time(storage: timetz) is Timetz; and Duration(as: parts) is IntervalParts, read as { months, days, micros }. The contract stores only the explicit type, so you can also write the explicit type itself. TimestampTemporal, a timestamp read as a Temporal.PlainDateTime, has no convenience form. A type read as a Temporal value needs a global Temporal, and Scalar fields says how to check for it.

The string types are ISO 8601 on every server, whatever its TimeZone and DateStyle: a timestamptz reads as the instant in UTC, such as 2024-01-01T00:00:00Z. The exception is infinity and -infinity, which PostgreSQL can store in a date or timestamp column: a string type reads them as infinity and -infinity, and a type read as a Date or a Temporal value fails to read them with RUNTIME.DECODE_FAILED. A JavaScript Date holds milliseconds, so a type read as a Date on a column with more digits of a second, such as DateTime(precision: 6), drops the rest. TimestampJsDate and TimestampInstant read a timestamp column as a Date and a Temporal.Instant, treating the stored date and time as UTC.

  • @id marks the primary key. @@id([a, b]) declares a composite key.
  • @unique adds a unique constraint on one field. @@unique([userId, title]) adds one across several fields.
  • @@index([...]) declares a secondary index.
  • @default(...) sets a database default: the database fills in the column when an insert leaves it out. The default is a literal, now(), autoincrement(), or any other SQL expression. Write the SQL as a sql tagged literal, which is sql followed by the SQL in backticks, such as @default(sql`gen_random_uuid()`). See Default values for how to write each kind of literal.
  • @onCreate(...) sets a value Prisma ORM generates when it creates the row, and @onUpdate(...) one it generates on every update. See Generated values.
  • @map("column_name") sets a field's column name in the database. @@map("table_name") sets the table or collection name when it differs from the model name. Without @@map, the table or collection has the model's name exactly as written, so model UserProfile is the table "UserProfile".
  • @@check(expression: sql`total >= 0`, name: "order_total_positive") adds a check constraint of your own to the table. See Check constraints.
  • @@control(observed) says how far Prisma ORM manages the table. See Control policy.

A field can be a list on PostgreSQL: tags String[] is a text[] column, and the same works for Int[] and the other scalar types. Prisma ORM adds a check constraint to a list column so it cannot hold a NULL element. To allow NULL elements, put the ? on the element type: String?[] allows null elements, String[]? allows a null list, and String?[]? allows both. In your code, String?[] is a ReadonlyArray<string | null>, String[]? is a ReadonlyArray<string> | null, and String?[]? is a ReadonlyArray<string | null> | null. A String?[] column has no check constraint, so use it for a list column that already exists without one. A list of an enum or of a named type works the same way, and so does a list of a value object, as Value objects shows.

How IDs map differs by database:

On PostgreSQL the primary key is an ordinary column, so pick its type and default yourself. On MongoDB the primary key is the document's _id, so type it ObjectId and map it to _id. Your code still names the field id, in rows, where, select, orderBy, and write data: @map changes only the name in the stored document. A field of a value object cannot take @map, because it is always stored under its own name.

Generated values

@onCreate(fn()) and @onUpdate(fn()) name a function that Prisma ORM runs in your application to fill the field: @onCreate when it creates the row and you leave the field out, @onUpdate on every update. The functions are:

  • uuid(), a version 4 UUID, the same as uuid(4), and uuid(7), a version 7 UUID.
  • cuid(2), ulid(), and ksuid().
  • nanoid(), 21 characters long, and nanoid(n), n characters long, from 2 to 255.
  • now(), the current time.

Each function makes a value for the field's type: uuid() works on String, Varchar(n), Char(n), and Uuid, and now() works on every PostgreSQL date and time type, Date, Time, and Timetz included. The database does not fill these columns, so a row written by raw SQL or another application gets no value. A field may have both a database @default and an @onCreate(...): createdAt DateTime @default(now()) @onCreate(now()) takes its time from your application when Prisma ORM creates the row, and from the database for other inserts. On an optional field, @onCreate(...) fills the field when you leave it out, and an explicit null is stored as null.

@onUpdate(...) alone generates nothing on create. If a required field has @onUpdate(...) and no @onCreate(...) or @default, you must pass a value for it in ORM create and upsert. To have it generated on create too, add @onCreate(...).

@default(uuid()) and the other functions that generate a value are refused in @default with PSL_GENERATOR_IN_DEFAULT, which names the @onCreate(...) to write. @default(now()) and @default(autoincrement()) stay: they are database defaults.

An argument a function does not take, such as uuid(5), cuid(1), or nanoid(300), is refused with PSL_INVALID_GENERATOR_ARGUMENT, and cuid() needs its version, cuid(2). An argument written with a fraction, such as nanoid(8.0), or in quotes, is refused with PSL_VALUE_TYPE_INCOMPATIBLE. The value a function writes must also fit its column: uuid() writes 36 characters, ksuid() 27, ulid() 26, cuid(2) 24, nanoid() 21, and nanoid(n) n, so String(storage: varchar, length: 5) @onCreate(uuid()) is refused when you run contract emit. A bare Char holds one character, and a varchar without a length has no limit.

For the column of a generated identifier, write its type alias. UuidString, Ulid, Nanoid, Cuid2 and Ksuid are Char(36), Char(26), Char(21), Char(24) and Char(27), as in id Ulid @id @onCreate(ulid()). The alias sets only the column, so the field writes @id and @onCreate(...) itself, and a foreign key that holds the identifier uses the alias alone, as in authorId Ulid. On SQLite, write the aliases in the sql namespace, such as sql.Ulid, and a fixed-length text column as sql.Char(n). On PostgreSQL a new schema can store a UUID in the native Uuid column instead, as id Uuid @id @onCreate(uuid(7)).

Prisma ORM 8 has no @updatedAt. To replace @updatedAt, write updatedAt temporal.UpdatedAt:

Prisma ORM sets the field to the current time on every create and update, and you can still set it yourself on a write. temporal.CreatedAt sets its field once, when the row is created. You do not import or declare temporal: it is a group of named types built into the contract syntax. On PostgreSQL the column is timestamptz.

Both take the time from your application's clock, not from the database, so the column has no database default, and a row you insert with raw SQL must supply the value. For a value the database generates, use DateTime @default(now()) instead.

temporal.UpdatedAt is written without parentheses. It is DateTime @onCreate(now()) @onUpdate(now()), a timestamptz(3) column your code reads as a JavaScript Date, and temporal.CreatedAt is DateTime @onCreate(now()). Write the attributes yourself for another type or a precision, such as DateTime(as: string) @onCreate(now()) @onUpdate(now()) for a string. The example at the top of this section writes them on a DateTime field only to show the attributes.

now() takes the column's precision and rounds the time down to it, so the value a create returns is the value PostgreSQL stores. A field written with as: temporal, such as DateTime(as: temporal) @onCreate(now()), needs a global Temporal for writes as well as reads. When your Node.js version has none, install temporal-polyfill and add import "temporal-polyfill/full/global" at the top of src/prisma/db.ts.

Columns of any database type

For a column of a database type no field type covers, write Raw(sql`...`) with the type written the way the database reports it. To see that text for a column that already exists, run prisma db schema:

Migrations create the column with that text, and db verify compares it with the type the database reports, so write integer, not int4, and quote a name that needs it, as in Raw(sql`"MyType"`). Your code reads and writes the value as unknown, and a default is a sql tagged literal. Raw("ltree"), without the sql tag, is refused. Raw works on PostgreSQL and on SQLite, which Prisma ORM 8 supports as an experimental package.

Default values

Write each default in a form its column can hold. A quoted string is text, for example, so it cannot be the default of a JSON, decimal, or floating-point column. When a default does not fit its column, contract emit fails with PSL_VALUE_TYPE_INCOMPATIBLE, pointing at the value you wrote, and the message says what to write instead, such as Expected a number. A single value on a list field fails with PSL_DEFAULT_LIST_EXPECTED, and text that is not a valid value of its kind, such as a json literal that is not a JSON document, fails with PSL_INVALID_LITERAL. The examples below show the form for each kind of column:

  • A JSON default is a json tagged literal: json followed by the JSON document in backticks. Write a JSON array the same way, as tags shows.
  • A decimal default is a bare number.
  • NaN, Infinity, and -Infinity are written without quotes, and so are true and false.
  • A text default is a quoted string.
  • A fixed date, time, or interval is a tagged literal named after the column's PostgreSQL type: timestamptz for DateTime and the other timestamptz types, and timestamp, date, time, timetz, and interval for the types of those names, as in @default(interval`P1D`). A timestamptz default is a point in time with a UTC offset, such as timestamptz`2024-01-01T00:00:00Z` , and a timestamp default has no offset, such as timestamp`2024-01-01 00:00:00` . A quoted string on one of these fields is refused, and the message shows the tagged literal to write.
  • A Bytes default is a bytea tagged literal holding the bytes as hexadecimal after \x, as payload shows. Base64 text is not accepted.
  • On SQLite, a DateTime default uses the datetime tag, as in @default(datetime`2024-01-01T00:00:00Z`), and a Bytes default the blob tag, which holds hexadecimal digits, as in @default(blob`68656c6c6f`).
  • Each default, and each member of an enum, is checked by the column's type, so a value the column cannot hold unchanged is refused: more characters than a varchar(n) or char(n) column takes, a number a numeric(p, s) column would round, more digits of a second than a TimestamptzTemporal(3) keeps, digits below a millisecond on a field read as a JavaScript Date, which cannot hold them (also on MySQL's DateTime), an integer outside the range of Int or Int(storage: int2), or text that is not a UUID on a Uuid field.
  • A date or time default that the field's type does not hold makes contract emit fail with PSL_INVALID_DEFAULT_LITERAL, and the message shows a text the field takes. That includes an offset on a timestamp, date, or time default, a missing offset on a timestamptz or timetz default, more than six digits after the decimal point (three on SQLite), and a date or time that does not exist, such as 2024-02-30. The CLI checks these defaults on Node.js 24 too, which has no built-in Temporal.
  • On a field typed with an enum block, the default is the member's name without quotes, as in @default(Low). On a pg.enum(...) field, it is the value the member stores, in quotes, as in @default("admin"). Enums covers both.
  • Any other SQL expression is a sql tagged literal, and it goes into the column default exactly as written. Write the current time as now() and a sequence as autoincrement(), not as sql`now()` or sql`autoincrement()`, which are refused.

Prisma ORM 7's dbgenerated("...") is not accepted, and contract emit reports PSL_UNKNOWN_DEFAULT_FUNCTION. Write the same SQL as a sql tagged literal instead, so @default(dbgenerated("gen_random_uuid()")) becomes @default(sql`gen_random_uuid()`). contract infer writes every default in these forms.

Indexes

@@index([...]) takes a list of fields, and on PostgreSQL the named arguments below. Either the list or expression: is required, and an expression: index needs a name::

  • expression: is the whole index expression as SQL, in place of the field list.
  • where: makes a partial index; it is the condition as SQL, without the WHERE keyword.
  • unique: makes a unique index. @@unique([...]) is a unique constraint, which is the usual way to say a value must be unique; use unique: on @@index when you also need expression: or where:.
  • type: picks the index method, such as "hash" or "gin".
  • name: names the index. The name in the database is not exactly what you typed: it gets an eight-character hash on the end, user_name_active_000a85d8, and if you change name: later, the next migration plan renames the index instead of dropping and recreating it. map: instead sets the exact name, for an index that already exists in the database, which is what contract infer writes for indexes it finds. Give one or the other, not both.

Advanced PostgreSQL shows when each kind of index is the right one. expression: and where: take a sql tagged literal, as @default does; a quoted string there is refused with PSL_VALUE_TYPE_INCOMPATIBLE. Inside the literal no quote is escaped, and it may span lines. Prisma ORM stores the SQL with its shared indentation and the blank lines at its start and end removed. The SQL goes into the database as written, so it uses column names, not field names (they differ when a field has @map), and you quote the names yourself. Prisma ORM does not check the SQL until the migration runs. On MongoDB, @@index takes different arguments; see MongoDB indexes.

Full-text indexes

@@fullTextIndex([...]) creates the GIN index that PostgreSQL full-text search uses. It takes one or more text fields, and it needs either name: or map:, but not both:

Each top-level item of the list is a weight group, strongest first, and an item can itself be a list of fields that share a weight. In post_search, a match in title or subtitle ranks above a match in body. An index takes one to four groups, a group cannot be empty, and a field can appear only once. In an index of several fields, Prisma ORM wraps every column in coalesce(column, ''), so the index does not change when a column becomes optional or required.

language: sets the text-search language, which tells PostgreSQL how to break the text into searchable words. It defaults to english, and you set it as in @@fullTextIndex([title], name: "post_title_search", language: "german"). where: makes it a partial index, as on @@index. A field typed pg.enum(...), a PostgreSQL enum type as Enums describes, cannot have a full-text index. PostgreSQL only.

To search an index, name it in the query: fns.fullTextMatches(indexes.post_search, q) in an ORM where callback, as Full-text search shows. The query then reads the index's fields, weights and language from the contract, so it searches exactly what the index covers and PostgreSQL can use the index. For a partial index, made with where:, PostgreSQL uses it only when the query's own where also implies the index's condition, so add that condition to the query and check the plan with EXPLAIN. You can also search one text field with its own fullTextMatches and fullTextRank functions, as in p.title.fullTextMatches(query, { language: "german" }); give that search the same language as the index, because PostgreSQL does not use the index for a search in another language.

Check constraints

@@check adds a check constraint you write yourself, on top of the ones Prisma ORM generates for enum and list columns:

expression: is the condition as a sql literal, using column names, as on @@index. name: and map: work as they do on @@index: name: for a constraint you are adding, and map: for one that already exists in the database under that exact name. A model can carry any number of @@check attributes. PostgreSQL only.

Prisma ORM also adds two check constraints of its own: one on every enum column, so it accepts only the enum's values, and one on every list column, so it rejects NULL elements. A list whose elements may be NULL is written T?[], and it gets no check, as Models and fields describes.

Control policy

@@control(...) says how far Prisma ORM manages the table, with one of four values:

managed (the default) The table must exist and match the model exactly. Create, alter, and drop it.
tolerated Declared columns must match; extra columns are accepted. Create it if missing; never alter or drop it.
external Declared columns must match; extra columns and constraints are ignored. Never touch it.

Mixins

A mixin is a named set of members you write once and include in several blocks. Declare it with the block's keyword followed by mixin, and include it with + and its name:

The contract is the same as if the mixin's members were written where the + line is, so User has the fields id, createdAt, updatedAt and email, in that order, and the index on createdAt, and Role has the members ADMIN, USER and GUEST.

  • A model mixin goes only in models, a type mixin only in composite types, an enum mixin only in enums, and a mixin for a block an extension adds, such as policy_select mixin, only in blocks of that keyword.
  • A field or enum member that the block already has, from its own body or from another mixin, is an error, and so is including the same mixin twice in one block.
  • A mixin's own attributes can name only its own fields, as @@index([createdAt]) does. A model's attributes can name the fields a mixin gives it, as in @@id([tenantId, id]).
  • A mixin cannot include another mixin, and it is not a type, so it cannot be a field's type.
  • A mixin declared in namespace auth { } is included from another namespace as +auth.Timestamps, and the types of its fields are looked up in auth.

The language server completes mixin names after +, and goes to, hovers, renames and colors them.

Named types

The types block gives a database column type a name you can reuse on many fields:

Fields then use ShortName like any built-in type. The name keeps the column decision in one place: a varchar(35) column rather than text. You do not have to name a type: a field can use the type directly, such as String(storage: varchar, length: 35), Decimal(precision: 10, scale: 2), Uuid, or TimestamptzTemporal.

A named type is shorthand: the contract stores the column type, not the name.

A named type can also set @default, @onCreate and @onUpdate, and every field typed by it gets them. In this example, TimestampString(3) is a PostgreSQL timestamp(3) column that your code reads as a string:

  • @id and @unique belong to a field, not to a type, so write them on the field, as slug does. On a named type they are refused with PSL_UNSUPPORTED_NAMED_TYPE_ATTRIBUTE.
  • A field may add any attribute its named type does not set. Here updatedAt adds @default(now()), a database default, so a row inserted outside Prisma ORM also gets a time. A field that repeats an attribute its named type already sets is refused with PSL_DUPLICATE_ATTRIBUTE.
  • A named type is built on a type or an enum, not on another named type.

Prisma ORM provides two named types you do not declare: temporal.CreatedAt, set to the current time on create, and temporal.UpdatedAt, set on create and on every update. Write them without parentheses, as createdAt does above. On PostgreSQL they store a timestamptz(3) column that your code reads as a JavaScript Date. They take no arguments. For a string, a Temporal value or a precision, write the type and the attributes yourself, such as DateTime(as: string) @onCreate(now()) @onUpdate(now()), as UpdatedAt above does.

Each form of BigInt gives your code a different kind of value:

Type Column In your code
BigInt bigint a JavaScript bigint
BigInt(as: number) bigint a JavaScript number; a read or write outside the safe integer range fails
BigInt(storage: numeric) numeric a JavaScript bigint of any size

In Prisma ORM 8 the field's type sets the column, so String @db.VarChar(35) from Prisma ORM 7 becomes String(storage: varchar, length: 35), and the @db. attributes are gone. Enums

An enum lists its members, and with @@type it can also say how their values are stored and what each member stores:

In pg/text@1, pg is PostgreSQL, text is the column type, and @1 is the version of how the value is stored and read. Write @@type("pg/int4@1") to store the values as integers instead. When a member has no explicit value, the member name itself is stored.

Each member's value is a value of the enum's type, written as a @default of that type is: a quoted string for text, a bare number for a number type, and a tagged literal for a date or time. A quoted member on a number type, such as Half = "0.5" under @@type("pg/numeric@1"), is refused, and the message shows what to write, here Half = 0.5. Two members may not store the same value. Prisma ORM compares the values, not the text you wrote, so on pg/numeric@1 the members 0.5 and 0.50 store the same value and are refused.

On MongoDB the same rule applies, with MongoDB's types. A quoted member is text (mongo/string@1), and true and false are booleans. Write a number bare, NaN and the infinities included, and a date or binary value with its tag, as in date`2024-01-01T00:00:00Z` or binary`aGVsbG8=` :

These members are refused:

  • A quoted member on a type that does not take text, such as Unknown = "NaN" under mongo/double@1. The error is PSL_VALUE_TYPE_INCOMPATIBLE, and its message says what to write.
  • A mongo/int32@1 or mongo/int64@1 member written with a fraction, such as 1.0. Write 1.
  • A mongo/decimal128@1 member that a Decimal128 would round, such as one with more than 34 significant digits. It is read as a Double, so the error is PSL_VALUE_TYPE_INCOMPATIBLE.

Do not use an enum on an Int64, Date, Decimal128, Binary or ObjectId type, or a Double enum with a NaN or infinite member, such as Ratio above. You can declare it, but it is refused when a collection Prisma ORM manages uses it, because the validator Prisma ORM writes for each collection cannot list those members.

Before 8.0.0-rc.20, MongoDB read a quoted member as JSON, so "NaN" was a number. A contract emitted before 8.0.0-rc.20 with a Decimal128 member written with leading zeros, such as "007.5", is refused when it loads: run npx prisma contract emit again.

On PostgreSQL, some types cannot hold enum members. JSON (pg/json@1 and pg/jsonb@1), byte strings (pg/bytea@1), text-search queries (pg/tsquery@1), time with a time zone (pg/timetz@1), vectors (pg/vector@1), and geometries (pg/geometry@1) are refused in @@type: use a text enum instead. For a PostgreSQL enum type, use a native_enum block, not @@type("pg/enum@1").

@@type is optional, and when you leave it out Prisma ORM picks the type from the member values: bare member names and string values give the database's text type, and integer values give its integer type. Give every member the same kind of value, because a mix of string and integer values throws an error whose code is PSL_ENUM_CANNOT_INFER_TYPE. A @default names the member, as in priority Priority @default(Low), even where the member stores a different value.

At runtime, db.enums holds each member as a query returns it, such as a bigint for pg/int8@1.

On PostgreSQL and SQLite, removing a member, or changing the value a member stores, changes rows that hold the old value, so migration plan and db update ask whether you renamed the member or want its value removed. Renames and data loss shows the answers.

An enum block is not a PostgreSQL enum type: the column is text or an integer. For a PostgreSQL enum type, declare it in a native_enum block and type the field pg.enum(Role):

Unlike an enum block, a native_enum block needs a value for every member. pg comes with @prisma/orm-postgres, so there is nothing to import. You do not create the PostgreSQL type yourself: npx prisma migration plan includes the CREATE TYPE. A field can name a native_enum declared in another namespace by putting the namespace first, as in pg.enum(auth.OrderStatus).

Value objects

A type block declares a value object: a structured value stored inside its parent row, with no table of its own.

A value object field can be optional or a list, and a type block can hold a field of another type. Watch the two spellings: types { ... } declares named types, and type X { ... } declares a value object. Storage differs by database: on PostgreSQL a value object field is stored in a single jsonb column, while on MongoDB it is an embedded document. Either way, contract.d.ts types it as a structured object rather than untyped JSON. On PostgreSQL, a table whose control policy is managed also gets a check on each value object column, named <table>_<column>_shape_<hash>, that accepts only a JSON object with every required field, each of its JSON type, and no other key. A value object is stored data, so changing one, such as renaming a field, changes the contract's storage hash, and migration plan writes a migration that replaces the check. That migration fails on a row the new check refuses, and the error names the check and the query that finds the rows. On MongoDB, whether to embed or reference is the central modeling decision, and MongoDB data modeling covers it.

Relations

Relations use the @relation syntax you know from Prisma ORM. The side that holds the foreign key declares the scalar field and the mapping, and the other side declares a list:

Add onDelete and onUpdate to the same @relation: they belong on the side that holds the foreign key, not on the list side, and each takes Cascade, Restrict, NoAction, SetNull, or SetDefault:

On a SQL database, each relation's foreign key gets an index on its columns, so that deleting or updating a referenced row can find the rows that point at it. If the model already has a plain index, a unique constraint or a primary key on exactly those columns, that one serves instead and no second index is created. A partial index, or one with a non-default type or options, does not count. To use an index whose first columns are the foreign key's, name it on the relation with index: "<name>", using the name or map you gave it; to have no index at all, write index: false. An unnamed @@index on exactly the columns of a unique constraint or the primary key is left out of the contract, because the unique one already serves its lookups.

When two relations join the same two models, as Authored and Edited do here, give each pair the same @relation("Name") on both ends so Prisma ORM can tell which list belongs to which foreign key; otherwise npx prisma contract emit fails with an error whose code is PSL_AMBIGUOUS_BACKRELATION. For a one-to-one, make the other side singular instead of a list, so User declares profile Profile?, and put @unique on the foreign-key field:

Many-to-many relations need a model for the join table, and you write that model yourself: there is no implicit many-to-many. That model must follow two rules: if a side has a composite primary key, that model needs one foreign-key field for each part of it, and its @@id([...]) must list exactly the foreign-key fields and nothing else.

You then read post.tags as a list of Tag, without mentioning PostTag in the query. Break either rule and npx prisma contract emit reports which list field it could not match to a model. If two models qualify, npx prisma contract emit throws an error whose code is PSL_AMBIGUOUS_BACKRELATION: put the same @relation("name") on both ends of one pair, so on PostTag.post for Post.tags.

For which shape to choose and which side owns the foreign key, see relational data modeling and MongoDB data modeling.

Row-level security

Two block kinds and one attribute declare PostgreSQL row-level security, and migration plan turns them into ENABLE ROW LEVEL SECURITY and CREATE POLICY statements. @@rls on a model turns row-level security on for its table. A policy_select, policy_insert, policy_update, policy_delete, or policy_all block declares one policy for one operation, and a role block declares a database role a policy names:

Policy and role blocks assign their settings with =, unlike model attributes. target names the model, which must carry @@rls; put the policy blocks inside the same namespace block as the model when it has one. roles lists bare role names. A role block, whose braces stay empty, names a role the policies refer to. Prisma ORM never creates or drops a role: create it yourself, and db verify fails when a declared role is missing. A role PostgreSQL always has, such as public, is written bare with no block: roles = [public]. using and withCheck are the two conditions as sql literals, using column names: policy_select and policy_delete take using, policy_insert takes withCheck, and policy_update and policy_all take either or both. permissive = false makes the policy AS RESTRICTIVE in PostgreSQL's terms, so a row must pass it as well as the permissive policies. The block's name becomes the policy name with a hash on the end, as index names do. A role block must be inside namespace unbound { }; unbound is a reserved word meaning "not in any schema", which is where a role belongs.

MongoDB indexes

On MongoDB, @@index and @@unique take a list of fields, each with an optional sort direction, plus MongoDB's own index options as named arguments, and @@textIndex declares a text index:

sort(field, Asc) or sort(field, Desc) in the field list sets a field's direction; this form is MongoDB only. Since 8.0.0-rc.17 the earlier field(sort: Desc) form is refused. The keys in weights are field names, quoted. The named arguments are type ("text", "2dsphere", "2d", or "hashed"), sparse, expireAfterSeconds, filter (a partial filter expression, written as a JSON string), default_language and languageOverride for a type: "text" index, include or exclude for a wildcard index, and the collation options collationLocale, collationStrength, collationCaseLevel, collationCaseFirst, collationNumericOrdering, collationAlternate, collationMaxVariable, collationBackwards, and collationNormalization. @@textIndex takes weights, language, languageOverride, filter, and the same collation options.

Every index in the contract has the name MongoDB stores it under, and migrations create and drop each index by that name. An index without a name is named after its keys and their directions, such as email_1, or createdAt_-1_authorId_1 for createdAt descending and authorId ascending. That is the name MongoDB gives an index created without one. To choose the name, write map: on @@index, @@unique, @@textIndex or @unique:

Without the map:, both indexes in this model would be named email_1, and MongoDB cannot hold two indexes with one name, so contract emit refuses the second with PSL_INVALID_INDEX. Two indexes on the same field in two variants of one base need a map: each for the same reason, such as @@index([title], map: "bug_title") on Bug and @@index([title], map: "feature_title") on Feature. An empty map: is refused.

[Upgrading a MongoDB project from before `8.0.0-rc.23`]

Index names are new in the contract, so every MongoDB contract with an index gets a new storage hash. An index without a name is named after its keys, such as email_1, which is the name earlier releases gave it in the database, so the database does not change. Earlier releases matched an index by its keys alone, so an index created under another name, such as by hand, also passed. It now fails db verify and db sign. Before you emit, list the names MongoDB holds, such as with db.users.getIndexes() in mongosh, and give each index whose name differs that name with map:, or with name in TypeScript. If two databases that share the contract hold one index under different names, one map: cannot match both, and MongoDB cannot rename an index: in one of them, drop the index and create it again under the contract's name, such as with dropIndex and createIndex in mongosh. Then run npx prisma contract emit, then run the mongo-index-names script from the upgrade instructions to add the names to the contract copies under migrations/snapshots/. Then run npx prisma db sign, or plan a migration, which has no operations, and apply it with npx prisma db migrate --advance-ref db. A script or test that matches an index operation id, such as index.users.create(email:1), now matches the name, as in index.users.create(email_1).

A wildcard index covers every field under a path, which is how you index documents whose keys you do not know in advance. Write wildcard() in the field list to cover the whole document, or wildcard(meta) to cover the fields under meta; the key becomes $** or meta.$**. include and exclude are lists of field names, quoted, that narrow what the index covers; give one or the other, and only with wildcard(). An index can hold one wildcard(), and it cannot be an @@unique, take expireAfterSeconds, or set a type: such as "hashed".

contract emit refuses, with PSL_INVALID_INDEX, any other index MongoDB would refuse, such as a type: "hashed" index on several fields, collation options without collationLocale, or a second text index in one collection. Two indexes in one collection with the same fields, options and name become one index, counting an option set to false as left out. So does a plain index beside a unique index on the same fields with otherwise the same options, such as @unique and @@index([email]) on one field: the contract keeps the unique index, which serves every query the plain one would. Indexes on the same fields with a different collation, partial filter or other option stay separate, so give one of them a name with map:. Two identical indexes with different names are refused with PSL_INVALID_INDEX, because MongoDB cannot hold one index twice: remove one, or give both the same name, which merges them. A TypeScript contract follows the same rules, as the MongoDB builder describes.

Base models and variants

A base model declares a discriminator field, the field whose value says which variant a row is. Each variant names its base and its discriminator value:

Field and model names are written bare, as type and Task are, while table names and discriminator values are quoted, as "task" and "bug" are. Rows whose type column holds "bug" are Bug records. A variant reuses its base model's fields, so a Bug has id, title, and type as well as severity and stepsToRepro. The base model can be declared before or after its variants. A variant does not declare an @id of its own: it takes the base model's primary key.

The discriminator field must be required and hold one value, so it cannot be optional (?) or a list ([]); since 8.0.0-rc.20 this holds on every database. It must also have a text type:

  • on PostgreSQL, String, Char(n) or Varchar(n);
  • on SQLite, String or sql.String(n), SQLite's text type with a length;
  • on MongoDB, String.

A named type for one of these, such as Kind = String on MongoDB, can type a discriminator too. On PostgreSQL and SQLite, your code reads the discriminator field as one of its variants' values, such as 'bug' | 'feature', not as any string. On PostgreSQL, a table whose control policy is managed also gets a check on the discriminator column, named <table>_<column>_check_<hash>, that accepts only those values. A field that breaks a rule is refused at @@discriminator with PSL_INVALID_ATTRIBUTE_ARGUMENT, as in must be required, but it is optional. Remove the "?". When a text enum types the discriminator field, each @@base value must be the value a member stores, such as "bug" for Bug = "bug", or contract emit lists the values you can write. A @@base value the field's type refuses, such as one longer than a Varchar(5) holds, is PSL_VALUE_REFUSED.

A variant can be in a different namespace block from its base, on PostgreSQL a different schema. Name the base with its namespace, as in @@base(a.Task, "chore"). In contract.json, the base model lists its variants by discriminator value, each naming the variant model and its namespace: "variants": { "bug": { "model": "Bug", "namespace": "public" } }.

You query a variant through the base model: db.orm.public.Task.variant('bug') returns the Bug rows only, and public here is the PostgreSQL schema. variant() takes the discriminator value from @@base, not the model name. Writing a row of a variant starts with the same variant('bug') call. See variant().

On a variant, @@map does more than rename: on PostgreSQL it chooses between two storage layouts. Give the variant its own @@map, as Bug has here, and its fields are in a table of their own that shares the base model's primary key. Leave @@map out and they are nullable columns in the base table. Relational data modeling covers choosing between the two.

On MongoDB, a variant adds its fields to documents in the base model's collection, so it declares @@base but no @@map of its own. Because the variant's fields share documents with the base model's, a variant field stored under a name a base field uses, such as the discriminator's, is refused with PSL_DUPLICATE_STORED_NAME. A variant field that restates a base field with a different stored name, type, optionality or list shape is refused with PSL_VARIANT_FIELD_DIFFERS_FROM_BASE: restate it exactly as the base declares it, or leave it out.

PostgreSQL extensions

A PostgreSQL contract can declare an extension it needs, such as pg_trgm, at the top level, which installs it in the public schema, or inside a namespace block, which installs it in that schema:

migration plan and db update create a declared extension that the database lacks, with CREATE EXTENSION IF NOT EXISTS, before the tables that use its types. Removing a declaration plans a DROP EXTENSION, which is destructive, so both commands ask first. db verify reports a declared extension that is not installed, and db sign accepts a database only when it has every declared extension. The contract records no extension version, because hosts offer different ones. contract infer writes an extension block for every installed extension except plpgsql and those a configured pack declares. An extension's name is unique across the database, so declaring one name in two namespaces is refused. An extension pack such as pgvector, PostGIS, ParadeDB or citext declares its own extension, so a project that composes the pack does not declare it: contract emit refuses such a declaration with PSL_ENTITY_DECLARED_BY_PACK, and migration plan and db update refuse it as a conflict. A pack declares its extension outside any schema, so db sign and db verify accept the extension in any schema on the connection's search path, such as the extensions schema Supabase uses. A TypeScript contract declares an extension with extension('pg_trgm') in its entities list, as the TypeScript builder shows.
