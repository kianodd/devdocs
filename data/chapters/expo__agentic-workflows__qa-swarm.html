QA Swarm is an automated workflow in which several coding agents test your app at the same time. Each agent gets its own cloud simulator and one short test flow. So a full pass takes as long as the slowest flow, not as long as all the flows in a row. Each verdict comes with screenshots and an evidence site.

How QA Swarm works

The highlighted steps run on Expo Workflows, Expo Simulators, and Expo Hosting:

  1. You start the workflow. You can give it the number of a pull request (PR) to report on.
  2. The workflow finds a build for each platform with the same native code, or it creates one. Then it adds the current JavaScript to the build.
  3. Each lane starts its own Expo Simulators session. A coding agent in the lane follows one flow and saves screenshots.
  4. Each lane deploys an evidence site with the verdict, the screenshots, and the session recording. The job of the lane fails when the verdict is not PASS.
  5. The workflow shows one report with the verdict of each lane. For a run with a PR number, it also posts the report on the PR.

A flow is a short Markdown file. You write one flow for each part of the app that you want to test.

Add the flows

Each lane runs one flow. Add a flow as a Markdown file in .eas/qa-flows. These two example flows work for most apps:

Then write flows for the important parts of your app. Keep each flow short, and give it these parts:

  • Steps: what a user does, in order, with the text that the user sees on the screen.
  • Out of scope: what the agent must not touch. Each lane has its own simulator, so the lanes do not share the data on the device. If your app saves data on a server, a flow that changes that data can break another flow that runs at the same time.
  • Pass condition: the result that a PASS verdict needs.

A file with the name <flow>.android.md or <flow>.ios.md replaces <flow>.md on that platform. Use it when a control works differently on Android and iOS.

Add the lane script

Each lane runs this script:

The script does these tasks in this order:

  1. It finds the flow file for the platform.
  2. It starts a session with the build. Then it writes the prompt, and runs the agent in the device mode.
  3. It uses eas-simulator-evidence to stop the session and build an evidence site. The site has the verdict, the screenshots, the action timeline, the performance charts, and the session recording. The tool deploys the site to Expo Hosting. It uses EXPO_TOKEN, the robot token from the device controller, to stop the session and deploy the site. The script removes the other tokens and the key of your agent from its environment. Read the code of version 0.2.4 before you use it, because the tool runs with the robot token.
  4. It ends with the verdict. The job of the lane passes only for a PASS verdict.

warning An evidence site on Expo Hosting is public. Each person who has the link can see the screenshots and the recording. To keep the evidence private, remove --deploy-alias from the command, and upload the folder that the tool builds to a private host.

Add the workflow

The workflow has one job for each lane, because Expo Workflows does not support matrix jobs. This example runs four lanes: the two example flows on Android and iOS.

The jobs do these tasks:

  • fingerprint, get_build_*, build_*, and repack_* find or create a build for each platform. A repack adds the current JavaScript to a build that already exists.
  • Each lane_* job runs the lane script with its platform and its flow. All the lanes run at the same time.
  • report shows the verdict and the evidence site of each lane on the page of the workflow run.

To add a lane, add a flow file, and copy a lane_* job with a new name and a new FLOW. Then add the new lane to the after list and the Markdown of report. If you test only one platform, remove the jobs of the other platform.

Read the result

When all the lanes finish, the page of the workflow run on expo.dev shows the QA Swarm report:

  • Verdict of each lane: PASS or FAIL, with one sentence from the agent.
  • Evidence site of each lane: the verdict, the report of the agent, the screenshots, the action timeline, the performance charts, and the session recording.

The job of a lane fails when its verdict is not PASS, so the workflow run shows each failed lane. The screenshots and the log of the agent are also in the artifacts of each lane job.

warning The verdict of the agent can be wrong. A FAIL can come from what the flow tells the agent, or does not tell it, and not from the app. Read the evidence site before you report a bug. To fix a false FAIL, add the missing facts to the flow, or to .eas/agents/app-facts.md for all the flows.
