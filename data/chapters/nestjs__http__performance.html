Nest doesn't talk to an HTTP server directly. It goes through an HTTP adapter, whose primary job is to proxy middleware and handlers to the appropriate library-specific implementations. This makes Nest framework independent: your controllers, providers, guards, pipes, and filters run unchanged on each of the adapters below, and you can migrate from one to another.

Adapter Package Built on
ExpressAdapter @nestjs/platform-express Express (the default)
FastifyAdapter @nestjs/platform-fastify Fastify
NodeAdapter @nestjs/platform-node The node:http module of Node.js

Hint

A framework adapter can only be implemented for a library that provides request/response pipeline processing similar to Express.

Choosing an adapter

Starting with NestJS v12.3, we recommend the NodeAdapter. It is the fastest of the three (see Performance), and its request and response objects come with the Express-style helpers, so most Express middleware, and most code written for the Express adapter, work with it unchanged. Nest still uses Express when you don't pass an adapter, so you need to opt in, as shown in Node adapter. In NestJS v13, the NodeAdapter will become the default.

Choose the FastifyAdapter to use Fastify plugins and features such as route constraints. Stay on the ExpressAdapter if your application relies on Express APIs that the Node adapter doesn't implement (see Express compatibility), or on a package that supports only Express.

Performance

In our benchmarks (wrk with 100 connections on Node.js 24, against a plain GET route, a GET route with a parameter, and a POST route with a JSON body), Nest handled about 50% more requests per second on the NodeAdapter than on the ExpressAdapter, and about 5% more than on the FastifyAdapter. To run the same benchmark on your machine, follow the steps in nestjs/nest#18063.

Keep in mind that the adapter handles only a small part of each request. A route that queries a database or calls other services spends most of its time waiting for them, so the choice of adapter matters most for lightweight routes at high request rates.

Express compatibility

Requests and responses are instances of NodeRequest and NodeResponse (exported from @nestjs/platform-node). They extend Node's IncomingMessage and ServerResponse with the Express-style properties and methods that middleware, exception filters, and @Res() handlers usually rely on, such as req.get(), req.is(), req.ip, req.ips, req.hostname, res.status(), res.send(), res.json(), res.set(), res.type(), res.cookie(), res.redirect(), res.sendFile(), and res.locals. Middleware runs in an Express-style stack and uses the same (req, res, next) signature.

Popular Express middleware packages, such as helmet, compression, cookie-parser, express-session, express-rate-limit, csrf-csrf, morgan, and passport (along with the @nestjs/passport guards), work as they do with the Express adapter. When a chapter of this documentation shows separate instructions for Express and Fastify (for example, Compression or Session), follow the Express ones.

The Node adapter deliberately differs from Express in a few places:

  • Routes are matched by specificity, as with Fastify, rather than in the order they were registered.
  • Paths are matched case-sensitively, for routes, middleware, and exclude() alike, as with Fastify.
  • A string returned from a route handler is sent as text/plain, not text/html.
  • req.path is the decoded path that the router matched, so a middleware that checks it sees the same path as the routes.
  • res.set() and res.type() don't append ; charset=utf-8 to the Content-Type header.
  • The adapter adds no ETag header, and a conditional request (If-None-Match, If-Modified-Since) gets the full response rather than a 304 Not Modified, as with Fastify, even if the handler sets ETag or Last-Modified itself. res.sendFile() and useStaticAssets() still send an ETag and answer with 304.
  • A route parameter longer than 100 characters doesn't match (see Node adapter options).
  • A JSON body with __proto__ or constructor.prototype keys is rejected (see Body parsers).

Some Express APIs are not available: res.render() (use the @Render() decorator instead), res.download(), res.format(), res.attachment(), res.contentType() (use res.type() instead), res.jsonp(), res.links(), res.location() (use res.set('Location', url) instead), res.vary(), req.accepts() and its variants, req.fresh and req.stale, req.host, req.range(), req.route, req.subdomains, req.xhr, mounting an Express application with app.use(), and Express settings, for which the adapter takes options instead (trustProxy for the trust proxy setting, for example).

Node adapter options

As with Fastify, route parameters are capped at 100 characters. A request whose parameter is longer falls through to another matching route, if there is one (a wildcard route, for example), and gets a 414 URI Too Long response otherwise. Behind a reverse proxy or a load balancer, connections come from the proxy, so req.ip is the proxy's address, and req.protocol is 'http' when the proxy terminates TLS. To read the client's address, protocol, and host from the X-Forwarded-For, X-Forwarded-Proto, and X-Forwarded-Host headers that a trusted proxy sets, pass the trustProxy option. As with Fastify, it takes true to trust every proxy, the addresses or subnets of your proxies (such as 'loopback' or '10.0.0.0/8', comma-separated or in an array), or a function that takes an address and its hop count and returns whether to trust it:

req.ip, req.ips, req.protocol, req.secure, and req.hostname then work as they do with Express, and so does sub-domain routing. Unlike the Express setting, the option takes no hop count: as with Fastify, a number trusts no proxy, since it cannot tell a proxy from a client that sends its own X-Forwarded-For header.

Warning

Trust only the proxies in front of your application. A client that can reach the application directly can send any X-Forwarded-* header.

Body parsers

The Node adapter comes with its own json, urlencoded, text, and raw body parsers, so it doesn't depend on the body-parser package. They take the same options as their body-parser counterparts, such as limit, inflate, strict, and type. As with Express, Nest registers the json and urlencoded parsers by default, and the rawBody option and the useBodyParser() method work as described in Raw body.

Like Fastify, the json parser rejects a body that tries to inject prototype properties: a body with a __proto__ or constructor.prototype key gets a 400 Bad Request response. To drop these keys instead, or to keep them (the body-parser behavior), set the onProtoPoisoning and onConstructorPoisoning options to 'remove' or 'ignore'. The urlencoded parser takes the same options.

Static assets and views

useStaticAssets() serves a directory with the serve-static package. It takes the options of that package, plus a prefix, as with Express. setViewEngine() accepts either the name of an engine, as with Express (see Model-View-Controller), or the options object of @fastify/view, with the engine and the templates directory.

Other packages
  • File upload: import FileInterceptor(), the other upload interceptors, and MulterModule from @nestjs/platform-node instead of @nestjs/platform-express. They are the same Multer-based interceptors, so the rest of the File upload chapter applies unchanged.
  • Serving a single-page application: the @nestjs/serve-static package (v12.1.1 or later) serves the files through the adapter, so it doesn't need the express package. Its fallback route for client-side paths requires @nestjs/platform-node v12.3.1 or later.
  • GraphQL: use the @nestjs/apollo driver (v14.1.1 or later), as with Express. The @nestjs/mercurius driver requires the Fastify adapter.
