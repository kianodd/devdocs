A middleware is an object you register on your client that Prisma ORM calls around every query your app runs. The cache middleware keeps the rows a read returned in memory, so when your app runs that same read again it gets the stored rows back instead of going to the database. Nothing is cached unless you ask for it: you mark a query with a cache annotation, and every query you do not mark runs against the database exactly as it did before. The store that holds the rows decides how long they stay usable. The default store keeps them for 60 seconds.

Reach for it when the same read runs over and over and you can live with an answer that is a little out of date, such as a dashboard, a lookup table, feature flags, navigation data, or a search result that is expensive to run.

The first call goes to the database as usual. For a SQL query builder read, the cache keeps the rows it got back, exactly as they came. For an ORM read, it keeps the value the method returned, so a nested include is cached with the rest of the call. If the same query with the same parameter values runs again while the store still holds the entry, Prisma ORM answers it from the stored entry and never calls the database driver.

You can set the following fields on the annotation:

Field Type What it does
bypass boolean Set it to true to send this one call to the database, ignoring anything stored
key string Your own string to store the rows under, instead of the one the cache works out
meta any value Data the cache hands to the store with the entry, such as tags; see Share one cache between instances

Every field is optional, and cacheAnnotation({}) caches the read under the key the cache works out. The type of the object is CacheAnnotationOptions.

bypass: true sends that one call to the database and leaves the stored rows untouched, so everyone else keeps getting the stored rows until the store drops them. A key is used exactly as you wrote it, and the cache adds nothing to it, so any two reads that pick the same key share one entry even when their parameter values or their models differ: the rows stored for id: 1 come back for id: 2 as well. When a read is served from the cache [#how-keys-and-hits-work]

Unless you give it a key, the cache stores a read under a key built from the query, its parameter values, and a hash of your contract, and it serves a read from the cache only when all three match. The same read with a different parameter value is therefore a separate entry and does not get the first one's rows.

That contract hash changes with any migration, whichever table the migration touched, so after a migration every entry the cache keyed for itself stops matching and none of them are served again. An entry you stored under your own key is not affected, because your key is used exactly as you wrote it and has nothing about your contract in it.

To change how the cache builds its keys, pass deriveKey to createCacheMiddleware. A common reason is to keep tenants apart, so that one tenant's cached rows are never served to another. deriveKey runs for every cached SQL query builder read that has no key of its own. Its first argument, exec, is the statement the read sends, with its parameter values. Build on the exported default, deriveKeyFromContentHash, so the key still covers the query, its parameter values and the contract hash. Two different queries must never get the same key, or one query's rows are served for the other. If deriveKey throws, the read fails.

Your own calling code cannot see the difference, because db.query(plan) and db.orm.public.User.first(...) give you the same rows whether the cache answered or the database did.

A read inside db.transaction(...), or on a connection you took out of the pool yourself with db.runtime().connection(), always goes to the database, and its rows are not stored. Code that holds a transaction or a connection expects to read back what it has just written, so the cache stays out of the way and you always see your own writes.

Check that caching is working

Prisma ORM has no counter or log option that reports cache hits, so to see them, register a small middleware of your own after the cache. When the cache answers a read, every middleware registered after the cache still gets activityStarted, activityEnded and activityFinalized for it, so your own logging and metrics keep recording it. Their intercept handlers are not called, and onRow does not run for rows the cache returned. The middleware below uses the activityEnded hook, which runs at the end of every query whether the cache or the database answered it. Its result argument has a field, result.source, that says who answered:

  • For a SQL query builder read, the hook sees the statement. result.source is 'middleware' when the cache answered and 'driver' when the database did.
  • For an ORM read, a hit sends no statement, because the cache answers the whole call. So the hook watches the ORM call instead, whose result.source is 'middleware' when the cache answered and 'client' when the call ran.

The other built-in middleware and the SqlMiddleware type are imported from @prisma/orm-postgres/family-runtime, which works with any SQL database. On MongoDB the same middleware is typed MongoMiddleware, from @prisma/orm-mongo/family-runtime, and works unchanged, because it reads only result.

Register cacheWatch() after the cache, by replacing the middleware line in src/prisma/db.ts and adding the import above it. Order matters for a middleware that returns rows itself instead of letting the query reach the database, because the first one to do that wins and the ones after it are never asked. cacheWatch() only logs. A middleware of your own that can return rows goes after the cache as well: the first middleware that returns rows answers the read, and you want the cache to answer the reads it holds.

Now call the same annotated read twice. With the SQL query builder, the first call prints driver, because it went to the database, and the second prints middleware, because the cache answered it. With the ORM API, the first call prints its statement with driver and the ORM call with client, and the second prints only the ORM call, with middleware. If you register other middleware of your own that can return rows itself, result.source is 'middleware' for all of them, so it tells you that a middleware answered and not which one.

Remove entries after a write [#remove-entries-after-a-write]

Writes do not clear anything on their own. A create, update, or delete leaves every stored entry where it was, so a read can keep returning the old rows until the store drops them. To remove entries, call invalidate on the middleware after the write:

invalidate({ keys }) removes the entries stored under those keys: the key an annotation named, or the key deriveKey returned. To remove the entry of an ORM read, give the read a key and pass that key to invalidate, as above. An ORM read without a key is stored under a digest of the call, which your code does not see. invalidate({ meta }) removes the entries whose annotation carried a matching meta, such as a tag. Only a store that indexes meta can do that; the default store throws RUNTIME.CACHE_STORE_META_UNSUPPORTED.

Call invalidate after the transaction that wrote the rows has committed. Called inside the transaction, another request can read the old rows before the commit and put them back. A read that started before invalidate and finishes after it does not store its rows, because they may be older than the write.

Otherwise, an entry stops being served when the store's lifetime for it runs out, or when the default store drops its least recently used entry to stay under maxEntries. A read that can never be even a second out of date is a read you should not annotate at all.

Options

These are the options you pass to createCacheMiddleware:

Option Type Default What it controls
store CacheStore createInMemoryCacheStore() Where the cached rows are kept and how long, for example in Redis
deriveKey (exec, ctx) => string | Promise<string> deriveKeyFromContentHash The key of a cached SQL query builder read whose annotation has no key. ORM reads do not use it

To change the size or lifetime of the default store, create it yourself with createInMemoryCacheStore and pass it as store:

Option Type Default What it controls
maxEntries number 1000 How many entries the store holds before it drops its least recently used entry
ttlMs number 60000 How long each entry lives after it is stored, in milliseconds. Infinity never expires
clock () => number Date.now The function the store calls for the current time

Common gotchas

Warning

The built-in store holds the rows in the memory of one process, so if you run two instances of your app each one keeps its own copy of the rows and fills it at its own pace, and every deploy starts both of them empty again. Two requests that run the same read can therefore get different rows depending on which instance served them, so never let a decision that has to be right rest on a cached read, such as a permission check or an account balance. Send those reads with bypass: true, or leave them unannotated.

Share one cache between instances

To have every instance read from the same cache, pass your own store. A store is an object with three async methods, so it can talk to Redis or to anything else your instances can all reach. The store keeps a version number for each key, starting at 0, and only unset changes it. The version is how the cache stops a read that overlapped an invalidate from storing old rows.

  • get({ key, meta }) returns an entry: { key, meta, version, data }, where version is the key's current version and data is { empty: true } when nothing is stored, or { empty: false, value } with the stored value.
  • set(entry, value) stores the value under entry.key only if the key's version still equals entry.version, and returns whether it stored it. Comparing and writing must be one atomic step, such as one Lua script on Redis. The store decides how long the value lives.
  • unset({ keys, meta }) removes the values under keys and increments each key's version, whether or not it held a value. A store that does not index meta throws when meta is set.

value is typed CachedValue, whose kind says which kind of read stored it:

  • { kind: 'statement-rows', rows } for a SQL query builder read: the rows as the database driver returned them. On PostgreSQL every value that is not SQL NULL is the text the database printed, and a NULL is null, so a createdAt column reaches your store as a string, such as '2026-09-17 08:00:08.775+00'.
  • { kind: 'call-result', result } for an ORM read: the value the ORM method returned, after Prisma ORM decoded it. It holds the types your code gets, such as a Date, a bigint or a class an extension returns.

Your store has to hand back from get a value equal to the one it was given, kind included, so turning values into something Redis can hold, and back again, is yours to write. Plain JSON is not enough: JSON.stringify throws on a bigint, and a Date comes back as a string. The example below is a store backed by Redis. It imports a serializer from ./serializer, which this page does not show: you write it as an object whose serialize(value: CachedValue): string and deserialize(text: string): CachedValue rebuild those types.

The version keys never expire. A version that falls back to 0 while a read is still running lets that read store old rows, and nothing bounds how long a read takes.

A store that indexes meta can group entries, for example by tag. Annotate the reads with cacheAnnotation({ meta: { tags: ['users'] } }), and cache.invalidate({ meta: { tags: ['users'] } }) passes the meta to the store's unset, which removes every entry with that tag. The cache never reads meta itself: the store decides what a meta means. Keep secrets out of meta, because other middleware can read annotations.
