important Data loaders are stable in SDK 58 and later. For SDK 55–57, enable unstable_useServerDataLoaders in the expo-router config plugin. They require either static rendering or server rendering.

Data loaders enable server-side data fetching for your routes. By exporting a loader function from a route file, you can fetch data on the server and access it in your component using the useLoaderData hook. This lets you keep sensitive data and API keys on the server while providing your components with the data they need.

This means you can safely use server-side secrets, database connections, and other resources that should not be exposed to the client. When using TypeScript, passing typeof loader as the generic parameter to useLoaderData allows the hook to infer the return type from your loader function.

info The useLoaderData hook does not need to be called in the route component itself. It can be called in any child component within the route's component tree.

Returning data

Loaders can return data as plain JSON, which is easily deserialized using JSON.parse. This includes objects, arrays or any other primitive that can be serialized with JSON.stringify.

If your loader returns undefined or null, the value is normalized to null.

Caching and revalidation

info This section describes SDK 58 and later. In SDK 55–57, Expo Router caches loader data on the client during navigation.

Expo Router uses loader data from the initial HTML response for hydration. When you revisit a route after it unmounts, useLoaderData fetches its data again. The platform HTTP cache uses Cache-Control to decide whether to reuse a cached response, revalidate it, or request fresh data. Expo Router does not keep a permanent in-memory data cache across route visits.

A revisit can display a Suspense fallback while the fetch completes, even when the platform serves a cached response. Retrying a loader error through the route's ErrorBoundary also fetches again.

Cache defaults

When a loader does not declare Cache-Control, these defaults apply:

Mode Default Cache-Control Applies to
Development no-store Loader responses
Server export no-store Loader responses
Static export private, must-revalidate, max-age=0 Loader data files and the HTML pages that embed their data

If the loader returns a Cache-Control header, it takes precedence over these defaults.

Static exports

In a static export, a loader's Cache-Control header applies to both the data file and the HTML page that embeds the data. Static exports keep only the Cache-Control header from loader responses.

The expo-server package, Expo Hosting, and npx expo serve apply these rules when serving your export. Other static hosts need their own header configuration. HTTP caching does not rerun a static loader. Its data changes only when you export and deploy the app again.

Difference between static and server rendering

Data loaders behave differently depending on your web.output configuration:

Aspect Static rendering Server rendering
Loader execution Build time Request time
request parameter undefined ImmutableRequest
Best for Blogs, marketing pages, documentation Personalized content, authentication-dependent pages

Static rendering

With static rendering, loaders execute during when exporting your app with npx expo export. The data is embedded in the generated HTML and JSON files. This means:

  • Data is determined at build-time and does not change until the next build
  • The request parameter is undefined because there is no HTTP request during the build
  • Ideal for content that does not change frequently

Server rendering

With server rendering, loaders execute on every request. This means:

  • The request parameter contains an immutable version of the incoming HTTP request
  • Requires expo-server for production deployment

Native apps

On native, a loader still runs on the server. The app fetches its data from that server, like an API route request.

  • Development: The app fetches loader data from the development server that npx expo start runs.
  • Production: Deploy your server. See Native deployment for more details.

Unlike web, native apps do not use server rendering, so loader data is not available on the first render. The first time a route renders, useLoaderData fetches its data and suspends. Add a `` boundary, or a layout SuspenseFallback to show a loading state while the data loads.

Known limitations

  • Loaders must return JSON-serializable data or a Response with a JSON body. Streaming loader data is not supported.
  • There is no public API to invalidate loader data for a route that remains mounted. Use Cache-Control to control HTTP caching when the route fetches again.
  • A loader export in a native-only route file, such as index.ios.tsx, does not run. Put the loader in index.web.tsx if that file exists, or in index.tsx if it does not.
